# AI 编程工作协议

> 生成到目标项目 `docs/B/B-06-门禁与工作协议.md`：定义 AI 参与开发时不可跳步的任务生命周期、证据标准与门禁生长机制。
> 引用方：SKILL.md Step 3 生成到目标项目 ｜ 关联：gates-templates.md、docs-skeleton.md
> 版本: v1.0

---

## 一、目的与适用范围

把「AI 高速生成 + 事后审计补漏」升级为「**契约前置 + 门禁自动化 + 缺陷闭环**」：让 AI 在动手前先对齐规范与先例，在提交前由门禁机器判定，在事后把每个缺陷沉淀为知识库模式或可执行门禁。

- **适用**：所有 AI 参与的开发 / 修复 / 重构 / 审计 / 文档工作。
- **不适用**：一次性只读分析（如"读一下这段代码解释逻辑"）可跳过步骤 4~6，但**仍须遵守第四章证据标准**——结论要给出 `文件:行号` 依据，不得凭印象下断言。

---

## 二、角色与职责

| 角色 | 定位 | 职责 |
|------|------|------|
| 人类 | 决策者 | 定优先级、批准 schema / 依赖变更、最终验收 |
| AI | 执行者 | 遵守本协议、主动跑门禁、主动回写文档、主动沉淀缺陷模式 |
| 门禁系统 | 裁判 | 机器判定红线，不通过即阻断；不因人、因任务而放宽 |

## 三、任务生命周期（7 步，不可跳步）

1. **读规范** — 固定顺序读取：`AGENTS.md` → 项目状态总览 → 相关架构文档 → 最近一次相关报告 / 台账。
   **产出**：一句话说明本次改动会碰到哪些模块、触碰哪些红线。
2. **查先例** — 搜 BUG 知识库是否已有同类模式；搜既有代码是否已有可复用实现。
   **红线：禁止重复造轮子**（已有封装 / 工具 / 组件优先复用）。
3. **定契约** — 前后端交互先定 DTO / schema，再动前端；schema 变更先写迁移脚本；权限隔离先确认三件套：角色注解 + 守卫 + 归属校验。
   **产出**：契约清单（字段 / 类型 / 约束 / 兼容策略）。
4. **列计划** — 用 TodoWrite 拆解任务，每项含**可机检的验收标准**（= 命令 + 期望输出）；计划中必须列出"要跑哪些门禁"。
5. **实施** — 小步提交；不修改与任务无关的代码；新增红线时**同时**新增门禁（见第七章）。
6. **跑门禁** — 至少跑与本次改动相关的门禁；**未通过不得声明"完成"**。
7. **回写文档** — 按改动类型回写：

   | 改动类型 | 必须回写的位置 |
   |----------|----------------|
   | 功能 / 模块变更 | 项目状态总览（模块状态、完成度） |
   | 缺陷修复 | `docs/B/B-04-BUG知识库.md`（新增或归类模式） |
   | 阶段进展 | 开发日志 / 迭代记录 |
   | 方案 / 架构决策 | 对应方案文档 + AGENTS.md 架构决策表 |
   | 新增代码规范 | AGENTS.md 强制规范 + 配套门禁 |
   | 文档增删 | 文档索引 + 跑文档校验脚本 |

## 四、证据标准

| 工作类型 | 最低证据形式 |
|----------|--------------|
| 代码改动 | `文件:行号`（Markdown 可点击链接），而非"我改了 xx 文件" |
| 编译 / 类型 | 命令 + 实际输出（粘贴真实输出） |
| 测试 | 命令 + 用例数 / 通过数 |
| E2E | 命令 + 通过数 + 关键断言 |
| 前端 UI | 无痕窗口截图或可复现的复测记录 |
| 线上 | 云端验证输出（日志 / 接口返回 / 监控） |
| 无法验证 | **显式标注「未验证 + 原因 + 风险」**，不得沉默跳过 |

**禁止**用以下表述替代证据：

```
❌ "应该没问题" / "看起来对" / "理论可行" / "业界通用做法"
```

## 五、完成定义（DoD）

- [ ] 红线符合（未触碰 AGENTS.md 阻断级红线）
- [ ] 契约已定（DTO / schema / 迁移脚本已就位）
- [ ] 门禁全绿（并留有执行证据）
- [ ] 迁移已提交并通过 review
- [ ] 文档已回写且文档校验脚本通过
- [ ] 新增红线已配对应门禁（或已标注 `[无门禁]` 并写明原因）
- [ ] 缺陷类任务已归类到 BUG 知识库模式
- [ ] 线上改动已部署验证，或显式标注"未部署"

## 六、缺陷复盘模板

每个缺陷修复后按下列模板沉淀（可写入 `docs/B/B-04-BUG知识库.md`）：

### 模式 &lt;XX&gt;：&lt;一句话症状&gt;

**症状**：&lt;用户 / 监控可感知的现象，一句话&gt;

**根因**：&lt;定位到 `文件:行号`，说明触发机制——为什么会发生，而不只是"哪里写错了"&gt;

**修复模板**：

❌ 错误写法：

```text
// 触发问题的写法
```

✅ 正确写法：

```text
// 修复后的写法
```

**预防措施**：

1. &lt;可执行的检查 / 规范条目&gt;
2. **对应门禁**：&lt;命令或脚本路径&gt;（如不可机检则标注 `[无门禁]` 并写明原因）

**实例**：&lt;文件链接&gt; + &lt;日期&gt;

---

**判定是否需要新增模式的方法**：

- 现有模式能覆盖 → **归入该模式并补一条实例**，不新建编号；
- 现有模式无法覆盖 → **新增编号**，并评估是否可以补门禁（可机检则走第七章流程，不可机检则标注 `[无门禁]`）。

## 七、门禁生长流程（6 步）

```
① 触发  修完一个缺陷 / 发现 AI 重复被纠正 / 新增了一条阻断级红线
   ↓
② 判定  四问（缺一不进）：可机检？ 零新依赖（只用项目已装工具）？ 真发生过或有明确证据？ 误报率可控？
   ↓ 可机检 → 建门禁        ↓ 不可机检 → 只写规范 + 标 [无门禁] + 归入 BUG 知识库模式
③ 生成  取配方：跨语言门禁配方表 → 组件 Gate 段 → 联网搜索（三层递进，与组件分类同机制）
   ↓
④ 注册  ① 写具体检查（scripts/checks/<id>.*）  ② 往 gates.json 追加一条（含 source / level / stage）
   ↓
⑤ 验证  负向验证：故意制造一次违规 → 确认门禁能拦住（拦不住则不得登记为 blocking）
   ↓
⑥ 登记  BUG 知识库 新增/归类模式 + docs/B/B-06 记录 + CHANGELOG（如发版）
```

**准入门槛四问的展开说明**（每条一问，为什么）：

1. **可机检？** — 只有机器能稳定判定的事件才配门禁；靠人主观判断的红线无法自动化，强做只会假绿。
2. **零新依赖（只用项目已装工具）？** — 门禁不得要求用户新装工具，否则用户会因成本而绕过门禁。
3. **真发生过或有明确证据？** — 只为实际踩过的坑建门禁，凭想象设防会堆出一堆无人触发的死门禁。
4. **误报率可控？** — 高频误报会让门禁被 `--no-verify` 绕过，宁可降为 `warn` 也不做高误报的 `blocking`。

**命中率现实预期**：真实工程中约 1/4 的缺陷模式最终会固化为门禁。**不是每个坑都要门禁**——不可机检或误报率高的，只写规范并标注 `[无门禁]`，靠 review 与知识库约束。

## 八、三条元规则原文

以下章节将被原样复制进 `AGENTS.md`：

```markdown
## 门禁即规则（元规则，优先级最高）

1. **无门禁不立规** — 新增"阻断级"红线时，必须同时提交可执行检查并登记入
   `scripts/gates.json`；确实无法机检的红线，标注 `[无门禁]` 并写明原因。
2. **缺陷必闭环** — 每修复一个缺陷，必须判定"是否可机检"：可机检 → 新建或扩展门禁；
   不可机检 → 归入 `docs/B/B-04-BUG知识库.md` 模式。禁止只改代码不沉淀。
3. **契约唯一源** — 跨端字段以 DTO / schema 导出物为唯一事实源，导出物变更须随代码
   一同提交（CI 校验漂移）。

> **门禁清单唯一事实源**：`scripts/gates.json` ｜ **统一入口**：`scripts/verify.*`
> ｜ **宪法一致性校验**：`scripts/check-constitution.*`
> **开工前置**：读取 `scripts/gates.json`，了解本仓库现有门禁（避免重复踩坑）。
```

说明：**元规则章节总长 ≤ 15 行**，细则一律外链（指向本协议与门禁清单），以防宪法膨胀。

## 九、违规处理

| 违规情形 | 处理方式 |
|----------|----------|
| 未跑门禁就声明完成 | 视为未完成，退回步骤 6 |
| 无门禁新增红线 | 驳回该规则，先补门禁或标注 `[无门禁]` |
| 只改代码不沉淀缺陷 | 补模式后方可合入 |
| 文档未回写 | 文档校验失败，阻断提交 |
| 越权 / 事务 / 硬编码等阻断级红线 | 按 AGENTS.md 红线处理（拒绝合入） |

## 十、上下文与文档纪律

**文档契约**：

- B / C 系列文档须有状态头：`> 版本: … | 更新: … | 状态: …`；
- 编号唯一，缺号须有归档文件或索引标注预留；
- 索引须覆盖全部非归档文档；
- 单篇超限（见 AGENTS.md 规模阈值）须拆分到 `docs/`。

**文档校验脚本用法**：`node scripts/docs-check.mjs`（error 阻断、warning 提示；退出码 0 = 无 error，1 = 存在 error）。

**记忆清理**：项目记忆季度清理；会话记忆保留最近 7 天。
