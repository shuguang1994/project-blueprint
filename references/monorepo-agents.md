# 多子项目 AGENTS.md 生成规则

> 多子项目（monorepo / 前后端分离）场景下 AGENTS.md 的「根 + N 包」生成规则。
> 由 `SKILL.md` Step 1.4 的探测结果驱动，Step 2 装配时引用（见 `references/step-1-discovery.md`、`references/step-2-assembly.md`）。
> 仅当探测到 ≥2 个子项目时启用；单项目不使用本文件，保持 v1.8.0 单文件行为（零变化）。

## 一、为什么这样做（就近原则）

AGENTS.md 的官方约定是 **就近原则（closest-file-wins）**：AI 编辑哪个目录下的文件，就读取离它**最近**的那一份 AGENTS.md。

| 方案 | 后果 |
|------|------|
| 单根大文件 | 各子项目规范全部堆在根文件里 → 根文件迅速膨胀（易破 300 行硬阈值）；每次上下文加载整份读入 → **无关包的信息挤占上下文预算** |
| 根 + 包级 | AI 改 `server/` 只读 `server/AGENTS.md` + 根文件 → 只加载相关规范，各包规范互不干扰 |

> 结论：**根文件放全局约束，包级文件放该包专属约束，同一内容只存在一处。**

## 二、判定条件（何时启用嵌套模式）

| 条件 | 结论 |
|------|------|
| 各子目录中发现 **≥2 个** 构建/清单文件 | **启用**嵌套模式：根 `AGENTS.md` + N 份包级 `AGENTS.md` |
| 仅 1 个构建/清单文件（单项目） | **不启用**：走单文件路径，行为与 v1.8.0 一致 |
| 子目录存在但其中无构建/清单文件 | 该目录**不生成**包级文件（避免噪音） |

「构建/清单文件」指 Step 1.1「文件名模式 → 类别映射」识别到的构建/清单类文件（如 `package.json` / `go.mod` / `pyproject.toml` / `pom.xml` / `Cargo.toml` / `composer.json` / `*.csproj` 等）——**本文件不固定清单**，一律以 Step 1 实际扫描结果为准。

> 判定只依赖 Step 1.4 输出的「子项目清单」条数，不预设目标项目的目录名。

## 三、根与子职责边界

| 内容块 | 根 `AGENTS.md`（全局约束） | 包级 `AGENTS.md`（包专属） |
|--------|--------------------------|--------------------------|
| 项目身份 | ✅ 项目名 + 一句话简介 + **子项目索引表** | ✅ 包名/路径 + 该包技术栈 |
| Boundaries | ✅ 仓库级 Allowed / Ask First / Never Touch | —（不重复） |
| 常用命令 | —（命令分布在各包） | ✅ 该包 dev / build / test / lint |
| Git 规范 | ✅ 分支 / 提交格式 / 禁止提交 / 双远程与发布 | —（不重复） |
| CI 与门禁装配 | ✅ `scripts/gates.json` / `scripts/verify.*` / `scripts/check-constitution.*` / 装配点 | ✅ 仅写本包门禁承诺（`Gate` 段）+ 本包检查命令 |
| 门禁即规则（元规则） | ✅ 三条元规则原文（注入 A） | —（不重复，用一句引用指向根文件） |
| 发布规范 | ✅ CHANGELOG / 版本号 / tag / 发布流程 | —（不重复） |
| 强制规范 | —（包专属规范下沉到各包） | ✅ 该包 Conventions（含 ✅/❌ 要点） |
| 模块速查表 | — | ✅ 包内模块 → 目录 → 职责 |
| 代码审查检查清单 | ✅ 仓库级清单 | —（包有专属清单时追加，不复制根清单） |
| 上下文管理 | ✅ 文档规模阈值 / 文档契约 / 维护职责 | ✅ 本包维护职责（一句话） |
| 工具增强层入口 | ✅ 指向各工具入口（见 `references/vendor-breadcrumbs.md`） | —（增强层统一在仓库根生成） |
| 跨包契约唯一源 | ✅（仅当存在跨包共享 DTO / schema 时写） | — |

**边界铁律**：

```
❌ 包级规范重复写进根文件
❌ 根级规范在每个包重复写一遍
✅ 同一内容只允许存在一处（唯一事实源）
✅ 包级文件用一句引用指向根文件，而非复制根文件正文
```

> Reason: 同一约束存在两处 → 改一处忘一处，AI 读到哪份取决于就近原则，等于随机行为。

## 六、增量合并策略

| 现状 | 动作 |
|------|------|
| 子目录已存在 `AGENTS.md` | **只补缺失章节**，保留已有内容（不覆盖、不重写） |
| 已有根 `AGENTS.md`、但无包级文件 | **只新增包级文件**，不重写根文件；提示用户根文件可精简为「全局约束 + 子项目索引」 |
| 根 `AGENTS.md` 已完善且已含子项目索引表 | 只补缺失的包级文件 |
| 子目录仅无构建/清单文件 | 不生成包级文件（不制造噪音） |

> 与 Step 1.0 的增量原则一致：已有项目接入只做补充，不推翻重来。

## 七、与门禁 / 规格文档的关系

- `scripts/gates.json` **仍在仓库根**，是门禁清单唯一事实源，**不按包分散**（分散即产生多个事实源）
- 包级门禁的表达方式：在清单条目上用 `cwd` 字段指向子目录（字段定义见 `references/gates-templates.md`，此处不重复）
- `scripts/verify.*`（统一入口）与 `scripts/check-constitution.*`（宪法自校验）同样部署在仓库根，全包共用
- 规格文档（`docs/` 骨架、B-01 / B-04 / B-06 等）默认位于仓库根；包内如需专属文档，按包内 `docs/` 组织，不与根 `docs/` 混编号

## 八、常见结构与输出对照

| 探测到的结构 | 输出 |
|--------------|------|
| `server/` + `admin/` + `client/` | 1 份根 `AGENTS.md` + 3 份包级 `AGENTS.md` |
| `packages/*`（monorepo，多个包含构建文件） | 1 份根 `AGENTS.md` + `packages/` 下每个含构建文件的目录各 1 份 |
| 子目录存在但无构建/清单文件 | 不生成包级文件（避免噪音） |
| 仅 1 个构建文件（单项目） | 只生成 1 份根 `AGENTS.md`（行为与 v1.8.0 一致） |

> **共享组件提升到顶层**：根目录的 `.eslintrc*` / `docker-compose.yml` 等跨包共享配置归属**根** `AGENTS.md`，不在各包重复（见 `references/step-1-discovery.md` 1.4）。
