# v2.0.0 功能发布说明 — 生成的 CI 不再「假绿」：门禁真的会跑，规范真的对得上

> 版本: v2.0.0 | 更新: 2026-10-14 | 状态: 已发布（`tag v2.0.0` 双远程推送）｜**含 Breaking Change**
> 升级方式: `npx skills update project-blueprint` 或 `dsh plugin --profile web add 'github:shuguang1994/project-blueprint#v2.0.0'`
> English version: [D-15-v2.0.0-Release-Notes-EN.md](D-15-v2.0.0-Release-Notes-EN.md) | 上一篇: [D-06-v1.9.0-功能发布说明.md](D-06-v1.9.0-功能发布说明.md)

## 一、一句话

**修掉「CI 看起来是绿的、其实什么都没查」的根因。**

如果你用 Project Blueprint 初始化过项目，这一版值得升级——它修的是**生成物本身**的问题，不是换个说法。三类最常见的"假绿"：

| 你看到的 | 真实情况 | v2.0.0 |
|----------|----------|--------|
| CI 全绿 ✅ | 测试步骤带着"允许零测试也判绿"的开关 → **一个测试没写也是绿的** | 开关删除。**零测试 = 红灯**（测试运行器本来就是这个默认行为） |
| CI 有"门禁"步骤 | 门禁 job 是一段需要你**手工粘贴**的片段 → 没粘上就从来没跑过 | 门禁 job **已内联**进生成的 workflow，不存在"忘了粘" |
| 门禁显示 ✅ | 项目没有源码目录 / 依赖清单时，检查**静默跳过**，只打一行 info | 改为显式声明「**不适用 + 原因 + 风险**」；能回退比对的就**真的去比** |

v1.9.0 让规范「铺得开、不跑偏」；v2.0.0 让规范体系**自己不出假绿**。

## 二、为什么做这一版

这些不是假想问题。三个真实项目里都出现过，且都能追到**同一份生成模板**：

| 现象 | 真实记录 |
|------|----------|
| 测试零用例仍判绿 | 某项目 CI 直接照抄模板的测试步骤；其自查结论原文：「因 spec 未入库，**CI 实际空跑（假绿）**」 |
| 门禁从未执行 | 某项目 Gitee Go 环境里插件未提供 `node`/`npm`，整个阶段 5 条命令**全部** `command not found` 秒退（流水线表面"已运行"）；其文档原文：「**CI 自建立起从未真正执行过任何一条门禁**」 |
| 40 条门禁只 5 条进 CI | 门禁以"追加片段"形式提供，人工接线时漏掉大部分 |
| 规范文件改名 → 校验静默失效 | 门禁用**章节名**引用规范条目，改名后无人发现 |
| 「违宪审查」只查一半 | 只查得出"门禁指向的规范没了"，**查不出"规范写了但没人守"** |

## 三、修了什么（逐条对照）

### 3.1 假绿开关：测试零用例不再判绿

- 生成的 CI 模板与组件知识库中，**14 处**「允许零测试」的开关**全部删除**
- 原因很简单：那些开关只做一件事——把"没测"伪装成"测过了"

| 测试运行器 | 零用例时的默认行为 |
|------------|--------------------|
| vitest / jest / mocha | 报 `No test files found`，**非 0 退出** |
| pytest | **退出码 5**（非 0） |
| Go `go test` | 无测试包即 0 退出（Go 内置语义如此，与"假绿开关"不同） |

**"零测试判红"本来就是默认行为**，所以修法是**删开关**，不是换一个开关。

**测试步骤怎么处理**：生成的 workflow 里，测试步骤带显式标记；按 Step 1 的探测结果二选一——

| 探测结果 | 动作 |
|----------|------|
| 探测到测试框架或测试文件 | **保留**该步骤 |
| 未探测到 | **删除**该步骤，并在 `docs/B/B-03-测试指南.md` 写明「建立测试后补 CI test 步骤」契约 |
| Go 项目 | `go test ./...` **无条件保留** |

### 3.2 门禁接线：不再依赖"记得粘贴"

- 四种语言（TypeScript/NestJS、Vue/React、Go、Python）的 workflow **已包含**门禁 job，直接调用 `scripts/verify.*`
- **"追加片段"这一步取消**——"忘了接线"这个失败模式不再存在
- 若你的项目**已有** CI 文件，脚本会跳过不覆盖；但生成报告会**核验其中是否真的调用了门禁入口**，缺失就显式标出「门禁未接线 + 风险」，不再沉默

**顺带修掉一个隐性坑**：旧模板让 CI 调用 `make verify`（Go）与 `python scripts/verify.py`（Python），但这两个宿主**从未被生成过**——引用一个不存在的东西，等于该步骤必然失败。本版补齐了**可直接运行的** Python 版门禁入口与宪法自校验，并加了一条硬性规则：**CI 里引用了哪个宿主，就必须真的生成它**。两个宿主的语义已实测一致（同一份门禁清单 → 同一批门禁 → 同一退出码）。

### 3.3 规范引用：改用稳定编号，改名不再断链

**旧做法的隐患**：门禁用章节名引用规范（`AGENTS#文档契约`）。你把这一章改名或重构，**没有任何检查会发现**。

**新做法**：

```
source: "AGENTS#RL-01@文档契约"
        └ 稳定编号（权威引用）┘ └ 仅供人读，改名不影响判定
```

- **稳定编号**：`RL-01`、`RL-02`……**只增不改、不复用**；要作废就把档位标成 `retired`，不删行
- **新增红线权威表** `docs/B/B-00-红线与门禁映射.md`：每行 = `编号 | 档位 | 红线内容 | 对应门禁 | 检查方式 | 无门禁原因`
- **为什么放 docs 而不是 AGENTS.md**：AGENTS.md 是索引层（≤ 300 行）。把清单塞进去就变成"两处各维护一份"，改名时必然漂移。**AGENTS.md 只做索引，清单只有一处。**
- **权威表与门禁清单同时生成**：只生成门禁清单会让双向校验退化，等于"装了一半"

### 3.4 BUG 知识库：编号格式统一，统计口径才能算得出来

**问题**：同一件事在生成路径上有 4 种写法，而"缺陷 → 门禁转化率"这个指标只按其中一种计数。实测两个真实项目按那个口径计数**都是 0**（真实条目分别有 142 条和 60 条）——**指标算不出来，等于没有**。

**新做法**：统一为 `## BUG-<NNN> | <标题>`（三位补零、唯一、不复用）+ 顶部症状速查表 + 六段式条目。文档骨架里明确写着这是**唯一格式**，另外四处（生成模板 / 条目内部结构 / 同步指南 / 统计口径）一律引用它。

### 3.5 空转门禁：不适用就说清楚，能比就真的比

**旧行为**：项目没有源码目录或依赖清单时，检查**直接跳过**，只打一行「跳过检查 A」——看起来绿，实际没检。

**新行为**（两件事都做了）：

| 做法 | 效果 |
|------|------|
| **必做**：打印适用性裁定 | 统一输出 `不适用｜原因：…｜风险：…｜裁定`，把"没查"和"查过没问题"彻底区分开（不改变退出码，不会误报红灯） |
| **回退比对** | 没有源码目录时，改用「**仓库顶层目录 ↔ 模块速查表**」比对。**纯文档 / 纯前端项目因此第一次真正被检到**（实测能报出"速查表写了 `src`，但该路径不存在"） |

回退模式带可编辑的噪音排除清单；「表里写了但路径不存在」报 `warning`（零误报），「目录存在但表里没有」只报 `info`（顶层目录常是工具/文档目录，不必然算"模块"，避免刷屏）。

**新增一条配套检查**：探测到测试框架 / 测试文件，但 CI 里找不到跑测试的步骤 → `warning`（"建了测试却没接进 CI"）。防止"为了不复现假绿，干脆把测试步骤删掉"变成新的静默缺陷。

### 3.6 违宪审查：两个方向都能查

**旧实现的两个问题**：

1. **只查单向**——查得出"门禁指向的规范没了"，**查不出"规范写了但没人守"**（后者更要命）
2. **生成侧用的模板还有代差**——它的判定依赖规范文件里的一类特殊标注，而生成侧**从不产出**这种标注 ⇒ 该规则**永远不报**。实测：三个演练项目上它输出「0 error / 0 warning / 0 info」——**跑了，但什么都没查**

**新实现**：

| 项 | 内容 |
|----|------|
| 双向校验 | ① 门禁引用的规范条目必须存在（防僵尸门禁）；② **档位为 `blocking` 的规范条目必须至少有 1 条门禁守住**（防"有规范无门禁"） |
| 旧格式兼容 | 章节名引用仍可解析，但会提示迁移（`warning`），不会直接报错 |
| **降级但不静默** | 没有权威表时：退回章节名兜底匹配，且**必须**输出两条提示——① 已降级；② **未覆盖的风险**（"查不出存在阻断级规范但没有任何门禁"）。**不允许静默给绿。** |
| 不因未建表而首日爆红 | 没有权威表时，定位失败降为 `warning`，建表后自动升回 `error` |

### 3.7 运行时自证：环境问题在第一行就暴露

每个 CI job 的**首条命令**改为自证运行时（`command -v` 检查 + 版本打印，缺则尝试自装）：

```yaml
- name: 运行时自证
  run: |
    command -v node >/dev/null 2>&1 && command -v npm >/dev/null 2>&1 \
      || (echo "[runtime] node/npm missing, installing" && (apt-get update -y && apt-get install -y nodejs npm \
          || (curl -fsSL https://deb.nodesource.com/setup_20.x | bash - && apt-get install -y nodejs)))
    node -v && npm -v
```

成本一行，收益是——**"缺运行时"出现在第一行**，而不是散成若干 `command not found` 被误读成"门禁失败"。托管 runner 上是空操作；自建机 / Gitee Go 上是救命的（见 §二 的真实记录）。

### 3.8 顺带修的同类隐患

以真实项目的审计结论为清单，反查生成路径，另修 4 处：

| 隐患 | 影响 |
|------|------|
| 项目里的质量评估文档引用了**已不存在的检查项编号** | 文档与实现脱节，读者被误导 |
| 旧模板引用 `make verify` / `verify.py` 却无实现 | 见 §3.2（幽灵宿主） |
| 种子门禁给的规范锚点与 AGENTS.md 模板标题**不同源** | 新项目首跑校验就会报错或静默失效 |
| BUG 库内部编号与文件名编号**不是同一编号空间** | 见 §3.4（编号语义漂移） |

## 四、升级指引（**含 Breaking Change**）

> 本次是 **major** 升级：**生成物的结构与校验口径变了**。已初始化的项目按下面 3 项迁移。**未迁移不会静默出错**——校验脚本会明确报出来，不会假装通过。

| # | 变化 | 你要做什么 | 不做的后果 |
|---|------|-----------|-----------|
| 1 | 门禁的 `source` 由 `AGENTS#<章节名>` 改为 `AGENTS#<编号>[@<章节名>]` | 给每条 `source` 补一个稳定编号，并在权威表登记同一编号 | 校验提示"用了章节名引用"（`warning`），改名后仍会静默断链 |
| 2 | **新增必生成产物** `docs/B/B-00-红线与门禁映射.md` | 新建该表，把现有规范红线按 `RL-NN` 编号登记 | 双向校验降级为单向（只剩"查僵尸门禁"），但会明确提示降级与风险 |
| 3 | BUG 库条目标题统一为 `## BUG-<NNN> \| <标题>` | 把 `### 模式 XX：` / `§2.NN 模式 XX` 改成新格式（正文与编号含义保留） | "缺陷 → 门禁转化率"的统计分母为 0（**指标算不出来**，不影响门禁运行） |

**不阻断的变化（可不迁移）**：`docs/B/` 的文档编号顺移一位（`B-03`→`B-04`、`B-04`→`B-05`、`B-05`→`B-06`、`B-06`→`B-07`），红线权威表占用新编号 `B-00`。已有项目按自己的索引走即可。

**升级命令**：

```bash
npx skills update project-blueprint          # 通过 skills.sh 安装的
dsh plugin --profile web add 'github:shuguang1994/project-blueprint#v2.0.0'   # 通过 DSH 安装的
```

## 五、验证方式（你可以自己复现）

本版不靠"应该没问题"下结论。**你可以用 3 个空项目自己验证**：

| 步骤 | 做什么 |
|------|--------|
| 1 | 在临时目录建 3 个最小项目：① Node + 已装测试框架 + 测试文件；② Node + **不装任何测试框架**；③ 纯文档（无源码目录、无依赖清单） |
| 2 | 对每个项目说一句「初始化这个项目的开发规范体系」，走完整初始化 |
| 3 | 对产物做这几项检查 |

| 检查项 | 期望结果 |
|--------|----------|
| 全文检索 `passWithNoTests` | **0 命中** |
| 生成的 workflow 是否调用门禁入口 | **有** `scripts/verify.` 调用 |
| 每个 job 的首条命令 | 含 `command -v` + 版本打印 |
| 测试步骤（形态 ①） | **有**测试步骤 |
| 测试步骤（形态 ②） | **无**测试步骤，且 `docs/B/B-03-测试指南.md` 写了补步骤契约 |
| 形态 ③ 的漂移检查输出 | 含「**不适用｜原因｜风险｜裁定**」或「切换为回退模式｜原因｜替代判据」，**不是**光秃秃一句"跳过" |

**负向验证**（确认检查真的会拦，而不是只会说好话）——可任选其一试：

| 制造的问题 | 期望被拦 |
|------------|----------|
| 在权威表里加一条没有门禁的 `blocking` 红线 | 报「**存在红线却无门禁**」错误 |
| `source` 引用一个不存在的编号 | 报「引用了不存在的编号」错误 |
| 把 CI 的测试步骤删掉（形态 ①，它明明有测试） | 报 `warning`：「建了测试却没接进 CI」 |

## 六、已知边界（如实说明）

| 边界 | 说明 |
|------|------|
| 本轮端到端验证覆盖 Node（有/无测试）与纯文档三种形态 | Go / Vue / React / Python 三种 workflow 的门禁内联、运行时自证、测试步骤规则**已就位并通过语法级检查**，但本轮未在真实项目上逐个跑一遍端到端 |
| 权威表是"可选但强烈建议" | 不生成它，双向校验会降级为单向（会明确提示），不会报假错 |
| 回退比对的方向一是 `info` 级 | 「目录存在但速查表没收录」在无源码根的项目上只提示不报警——顶层目录包含工具/文档目录，报 `warning` 会刷屏 |
