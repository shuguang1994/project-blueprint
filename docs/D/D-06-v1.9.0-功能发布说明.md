## 一、本次更新一句话

**把 v1.8.0 的「规范管得住」推进到「跨栈都通用、规范不漂移」——技能正文瘦身为按需加载的索引层，多子项目按官方就近原则生成嵌套 AGENTS.md，并新增第二条种子门禁把「代码/依赖 ↔ 规范」的不一致变成可机检事件。**

v1.8.0 解决「规范**管得住、活得下去**」，v1.9.0 解决「规范**铺得开、不跑偏**」。

## 二、为什么做这次更新

[D-05 行业对标与体系完备性评估报告](D-05-行业对标与体系完备性评估报告.md) 对 v1.8.0 做了「本地实证 + 联网对标」双轨评估，结论为**完备性 9/10、通用性 7/10、系统性领先度 7.5/10**，并暴露 10 项可验证差距，集中在三处：

| 缺口 | 影响 |
|------|------|
| `SKILL.md` 正文 **1012 行 / 50,203 字节** | 超 Anthropic 官方「SKILL.md 正文 < 500 行」建议 **2 倍**；渐进式披露只有 2 层，正文一次性全量载入，挤压上下文预算 |
| Monorepo 缺官方标准语义 | AGENTS.md 官方约定是**就近原则（closest-file-wins）**，而本 Skill 原先把各子项目规范「分块写进根单文件」——大仓必然膨胀、且丢失就近语义 |
| 缺「代码/依赖 ↔ 规范」漂移门 | 只有「文档内部一致性」（`docs-check`）与「红线↔门禁一致性」（`check-constitution`），而**行业公认第一大缺口正是规范漂移**（10,008 仓库实证：agent 配置 58% 只有单次提交历史、修订率仅 0.4 commits/月） |

另有 7 项通用性与一致性差距（知识库偏 Web 全栈、spec 驱动未成流程、只有 breadcrumbs 无工具私有增强层、本仓库自身门禁空转、对外数字口径漂移、无质量评估基准）。本次一次性补齐。

## 三、核心更新

### 3.2 Monorepo 嵌套 AGENTS.md（对齐官方就近原则）

- **判定条件**：各子目录中发现 **≥2 个**构建/清单文件（`package.json` / `go.mod` / `pyproject.toml` / `pom.xml` / `Cargo.toml` / `composer.json` / `*.csproj` 等）
- **生成物**：根 `AGENTS.md`（**全局约束 + 子项目索引表**）+ 各子项目目录下的包级 `AGENTS.md`（包技术栈 / 包命令 / 包强制规范 + `Gate` 承诺 / 包模块速查表 / 指向根文件的一句引用）
- **单一事实源铁律**：同一约束只允许存在于一处——包级规范不进根文件，根级规范不在各包重复
- **单项目零变化**：仅 1 个构建文件时行为与 v1.8.0 完全一致（只生成根文件）
- **增量友好**：子目录已有 `AGENTS.md` 只补缺失、不覆盖；根门禁清单 `scripts/gates.json` 仍在仓库根，包级门禁用 `cwd` 字段指向子目录，不按包分散
- 新增参考文件：`references/monorepo-agents.md`

### 3.3 规范漂移门（第二条种子门禁）

新增零依赖参考实现 `references/drift-check.mjs`，把「代码/依赖 ↔ 规范」的不一致做成可机检事件，含三类检查：

| 检查 | 内容 | 判定 |
|------|------|------|
| A｜依赖 ↔ 规范漂移 | 解析 `package.json` / `go.mod` / `requirements*.txt` / `pyproject.toml` 依赖，比对 `AGENTS.md` 技术栈行是否提及 | 未提及 → `warning`（含可配置忽略清单，避免构建工具噪音） |
| B｜模块速查表 ↔ 实际目录 | 比对源码一级子目录集合与 `AGENTS.md` 模块速查表 | 双向差异 → `warning` |
| C｜门禁有效性 | `gates.json` 每条 `run` 引用的脚本是否存在 | 不存在 → `error`（僵尸门禁） |

**种子门禁由 1 条升级为 2 条**：`docs-consistency`（文档一致性）+ `spec-drift`（规范漂移）；分级沿用「新项目 `blocking` / 存量项目 `warn`」。知识库跨语言门禁配方表同步新增 3 条漂移类配方（依赖清单 / 模块速查表 / spec ↔ 代码，并与既有「契约漂移」行明确分工）。

### 3.4 知识库 5 域扩展（15 个组件条目）

`references/knowledge-base.md` 新增 5 个维度章节，共 **15 个组件条目**，每条均含 `Commands` / `Conventions` / `CI job` / `Gate` **四段**：

| 新增域 | 条目数 | 组件 |
|--------|:---:|------|
| AI/LLM 栈 | 4 | LangChain / LangGraph、LlamaIndex、pgvector、Ollama / vLLM |
| IaC 与云原生 | 3 | Terraform、Helm、Kubernetes manifest（kubectl / kustomize） |
| 可观测性 | 3 | OpenTelemetry、Sentry、Prometheus + Grafana |
| 数据工程 | 2 | dbt、Airflow |
| 原生移动 | 3 | Flutter、SwiftUI（Swift）、Jetpack Compose（Kotlin） |

同步扩展探测规则：`step-1-discovery.md` 的文件名模式表 **+8 行**、命名模式推断表 **+6 行**（覆盖 `terraform` / `helm` / `dbt` / `opentelemetry` / `pubspec.yaml` / `build.gradle.kts` 等）。知识库现状：**917 行 / 18 个二级章节（16 个技术栈维度）/ 95 个组件条目**（命令与版本均经联网核对）。

### 3.5 规范驱动开发六阶段

新增 `references/spec-driven.md`：**specify → plan → tasks → checklist → implement → verify** 六阶段，每阶段定义**产物 + 准入门槛**（未过门槛不得进入下一阶段）；含三件套模板与「`checklist` 可注册为门禁」规则（`source: spec#<change-id>`，复用既有 `gates.json` 七字段，不新增字段）。`step-3-docs.md` 的 3.3 小节由「仅说明三件套格式」升级为流程落地；`docs-skeleton.md` / `project-sync-guide.md` 同步（新增「规范漂移修复」同步场景）。

### 3.6 工具私有增强层

新增 `references/vendor-breadcrumbs.md`：除原有 **5 条基线 breadcrumbs**（`CLAUDE.md` / `.cursor/rules/project.mdc` / `.github/copilot-instructions.md` / `.gemini/GEMINI.md` / `.windsurfrules`）外，按探测到的工具生成**私有增强层**：

- **Cursor**：`alwaysApply` 总入口 + 按目录 glob 的分层规则（只写该目录特有的非显而易见约束）
- **Claude Code**：`CLAUDE.md` 指向 + `.claude/settings.json` 中调用 `scripts/verify.*` 的 hooks 骨架 + `.claude/agents/` 子代理骨架
- **Copilot**：`.github/copilot-instructions.md` + `.github/instructions/*.instructions.md`（带 `applyTo`）
- 附带**防漂移条款**：增强层不得复制规范正文（否则产生第二事实源），冲突时以 `AGENTS.md` 为准；配置文件已存在时只追加、不覆盖

### 3.7 本仓库自吃狗粮（`scripts/` 门禁层）

Skill 一直为**别的项目**生成门禁层，本仓库自己却没有——`docs-check` 在本仓库运行时 5 条检查**全部因 `docs/B`、`docs/C` 不存在而跳过**（`0 error` 是假绿）。本次修复：

| 动作 | 结果 |
|------|------|
| `docs-check.mjs` 校验范围自适应 | 遍历 `docs/` 下**实际存在**的子目录（缺失目录不再整块跳过），新增编号冲突 `error` 判据；向后兼容（`docs/B`、`docs/C` 存在时行为不退化，经沙箱对比验证） |
| 新增本仓库门禁层 | `scripts/gates.json`（2 条门禁）+ `scripts/verify.mjs`（统一入口，支持 `--stage=`）+ `scripts/check-constitution.mjs`（规则 A~D） |
| 负向验证 | 编号冲突文档 → `1 error` exit 1；无状态头文档 → warning 不阻断；验证后彻底还原 |
| 新建文档索引 | `docs/README.md`（A~E 分类约定 + 维护规则 + D 级登记），使存量 warning **5 → 1 → 0** |

> 设计说明：skill 侧的校验脚本（`docs-check.mjs` / `drift-check.mjs`）作为**参考实现**保留在 `references/`，不复制到 `scripts/`（避免两份事实源）。

### 3.8 量化评估基准

新增 `references/eval-baseline.md`：**规模指标**（`SKILL.md` ≤ 200 行 / step 文件 ≤ 500 行 / `AGENTS.md` ≤ 300 行 / 单篇文档 ≤ 600 行 / 知识库单文件 ≤ 950 行 / 代码围栏闭合为 error 级）+ **闭环指标**（缺陷→门禁转化率、门禁覆盖率，含数据来源、计算方式与误判风险）+ **3 类 golden case 期望产物清单**（TS monorepo / Go 后端 / Python 数据管道，只定义期望与校验点、不建样例仓库）。

### 3.9 对外数字口径唯一化

以知识库实际内容为唯一口径，修正 5 处漂移：参考文件索引补齐至 **24/24 对齐**；技术栈维度清单 11 → **16**（并补 5 个新维度的联网回退搜索模板）；组件条目层级统一为 `### [组件名]`；知识库头注由「每个组件四段」改为准确表述（95 个条目中 27 个含 `Gate` 段）；MCP 口径统一为「§一 匹配表 14 行 + §二 18 个工具条目」。

## 四、使用方式

| 场景 | 行为 |
|------|------|
| 新项目初始化 | 单项目 → 只生成根 `AGENTS.md`（与 v1.8.0 一致）；多子项目 → 根 + 各包级 `AGENTS.md`；同步播种 **2 条种子门禁** |
| 已有项目接入 | 增量路径不变：只补缺失、不覆盖；包级 `AGENTS.md` 已存在时只补缺失章节 |
| 日常开发 | 门禁经 `scripts/verify.*` 统一入口在 pre-push / CI 执行；依赖或目录变更后由 `spec-drift` 报出规范漂移，按 `references/project-sync-guide.md` 的「规范漂移修复」场景回写 |
| 大型变更 | 走 `references/spec-driven.md` 六阶段（specify → plan → tasks → checklist → implement → verify），checklist 可机检项可直接注册为门禁 |

## 六、向后兼容性

## 七、已知限制与后续方向

- **`drift-check.mjs` 的检查 A 仅覆盖 Node 系依赖清单**（`package.json`）——非 Node 项目该检查输出 `info` 跳过；`go.mod` / `requirements*.txt` / `pyproject.toml` 已支持，Java（`pom.xml`）与 Rust（`Cargo.toml`）待补
- **Monorepo 嵌套模式尚未在真实多子项目仓库上端到端实跑**（规则与链路已落地并交叉引用验证）
- React 生态 UI 库（MUI / shadcn/ui）仍未列入知识库，依赖联网回退；知识库仍缺 Fastify / Actix-web 条目
- 知识库 **917 行**已接近 950 行上限，后续扩展需按维度拆分（拆分方案见 `eval-baseline.md` 规模指标）
- 3 层以上多子项目嵌套仍可能需手动再触发一次；Gitee 项目已有 GitHub Actions 时不会主动建议 `.gitee-ci.yml`
- 后续可考虑：把 `drift-check.mjs` 移植为 Python / shell 等价实现，覆盖更多宿主；补齐非 Node 依赖清单解析
