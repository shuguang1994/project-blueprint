### 2.1 核心机制：整改闭环（最值得引入的部分）

源项目跑通的完整整改链路（以 B-63 → B-64 为例）：

```
① 排查报告（B-63/B-64：只读审计，P0/P1/P2/P3 分级 + 契约不一致清单
              + 历史结论核验 + 门禁实跑基线 + 「未修改任何业务代码」声明）
        ↓
② 遗留清单（B-59：把报告项拆成 定位 / 方案 / DoD / 门禁 四要素可执行项）
        ↓
③ spec（.trae/specs/fix-b63-full-remediation/：spec.md 四段式
       + tasks.md 勾选式 SubTask（含 file:line）+ checklist.md 验收清单）
        ↓
④ 实施 + 跑门禁（未通过不得声明"完成"）
        ↓
⑤ 复核（逐条核验：已修复 91 / 部分修复 1 / 顺延 0，不采信"应该没问题"）
        ↓
⑥ 部署验证（云端冒烟 + 迁移落地核验 + PM2 重启号留证）
        ↓
⑦ 回写（B-63 文档内版本演进 v1.1/v1.2/§12.x 追加 → B-13 新增模式 → B-02 状态卡
       → B-12 开发日志 → CHANGELOG「验证/未闭环」→ docs/README）
        ↓
⑧ 门禁补强（本轮新增的任何红线，必须同时提交可执行检查）
```

> 这套闭环把"AI 高速生成 + 事后审计补漏"升级为"契约前置 + 门禁自动化 + 缺陷闭环"——见 [B-47 §一](源项目/docs/B/B-47-AI编程工作协议.md)。

## 五、引入时的适配要点（风险提示）

1. **编号冲突**：本项目 `docs-skeleton.md` 中 `B-02 = 部署指南`，源项目 `B-02 = 项目状态总览 + B 系列权威索引`。若引入"权威索引"概念，建议**不占用 B-02**，改为在 `docs/README.md` 内定义索引角色，或把"状态总览"作为可选文件 `B-0x`（按需生成）。
2. **避免过度工程**：`docs-check`、工作协议、门禁脚本对**小型项目（< 20 文件 / 单人）属于负担**。建议按规模阈值触发（如源码文件 > 30 或已发生 > 3 次回归缺陷时才生成），默认不生成——与现有"按需生成"原则一致。
3. **脚本语言中立**：源项目 `docs-check.mjs` 是 Node 脚本。Go/Python/Java 项目应由 Step 1 探测结果决定脚本语言与落点（可生成 `.py` / `.sh` 等价实现），不能硬绑 Node。
4. **warning 基线的历史债**：源项目 18 篇存量文档缺状态头（19 warning）说明"事后补规范"代价高。我们应把**"新增即达标 + 存量逐步补"**写进 P0-3 的校验策略，而非要求全量达标。
5. **元规则的双刃剑**：源项目"无门禁的规则不得写入 AGENTS"很强，但会让初始化阶段的 AGENTS 变得极简（许多规范因无门禁而不能写）。建议弱化为：**"新增红线口头约定 → 标注 `[无门禁]`；若为阻断级红线 → 必须同时给出检查方式"**。
6. **数据一致性判据可复用性高**：源项目"以 DB 为权威源、判断该值有没有生产者"的判据（[B-13 §2.73](源项目/docs/B/B-13-BUG知识库.md)）在"枚举多处定义不一致"场景高度通用，建议作为 `ai-common-mistakes.md` 新增条目（"权威源判定"类）而非领域规则。

## 七、开源产品视角的收益评估（2026-09-13 补充）

> 前六章的"通用性/可执行性/规模适配"是**内部维护视角**；本章回答"作为一个开源项目，这次升级能带来什么"。

### 7.1 结论：产品定位的质变，而非功能量变

| 维度 | 升级前（v1.7.1） | 升级后（v1.8.0 候选） |
|------|------------------|----------------------|
| 对外叙事 | 「扫描项目 → 生成 AGENTS.md + docs 骨架 + CI」= **模板生成器** | 「生成的红线**每条配一条能跑的命令**；docs-check 查文档、verify 挡 push」= **规范执行器** |
| 产物性质 | 静态 Markdown（几十个 `> 待填写` 占位） | 静态规范 + **可执行校验层**（脚本 + 门禁入口） |
| 可复制性 | 模板易被抄走（AGENTS.md 模板满天飞） | 设计不易被抄（规则↔门禁映射 + 闭环机制） |
| 用户回访理由 | 弱（初始化一次即结束） | 中高（脚本常驻用户仓库，漂移即报错） |

### 7.2 五层用户侧收益

| 层 | 用户得到什么 | 强度 |
|---|------|:---:|
| 产物性质 | 从"空目录骨架"到"当天可跑出结果的工具链" | 高 |
| 激活率 | 首日跑 `docs-check` 必然有输出 → 有"被检查"的实感，替代"面对空占位文件不知从何下手" | 高 |
| 留存 / 复访 | 门禁脚本长期跑在用户仓库 → 用户有了回来看 Skill 更新的理由（一次性工具 → 常驻机制） | 中高 |
| AI 协作质量 | 7 步协议 + DoD + 证据标准直接约束用户项目里的 AI 行为（用户最难自己写出的部分） | 中高 |
| 口碑可信度 | README 从"我会生成什么"升级为"我生成的东西可验证"，可附实战战果 | 中高 |

### 7.3 新增护城河路径：门禁脚本库

现状唯一护城河是 **70+ 组件知识库**（且靠联网回退可被部分替代）。引入门禁层后出现第二条路——**`check-*.mjs` 脚本库**：

- 社区可**贡献**脚本（"我踩过 Fastify 这个坑，写了检查"）
- 贡献门槛低（新增单文件脚本 vs 改核心 SKILL.md）
- 越多人贡献越难被替代
- 对比：知识库是"我们写、别人用"；脚本库是"大家写、生态长"——后者才是开源项目的复利来源

### 7.4 必须设计好的三个负收益点

1. **存量项目首因效应**：已有项目一装就报出"18 篇缺状态头 + 编号缺号"，会被吓退 → 必须默认 **warning 不阻断 + 存量豁免基线**（源项目自身 0 error/19 warning 即此策略）
2. **体积稀释卖点**：对外口径 "15+ 文件"会变成 "30+ 文件" → README 同步改为「**按需生成，小型项目保持精简**」，把精简也做成卖点
3. **小型项目体验倒退**：单人 5 文件项目跑 17 步门禁 = 纯负担 → 严格按规模阈值触发（见 §五.2）

### 7.5 诚实边界

- 开源增长（star/fork）主要由**定位清晰度 / 可发现性 / README 前 20 行**决定，本次升级对**拉新贡献间接且中等**；它改变的是**留存与推荐意愿**
- 若只做"多几个模板"而不做"可执行的校验层"，则不构成差异化，收益大幅缩水
- **一句话**：这次升级把定位从"规范生成器"推到"规范执行器"，是唯一能让别人无法用"不就是几个模板吗"打发的改动

## 八、自适应门禁能力评估与 P0-3 修正（2026-09-13 补充）

> 问题：本 Skill 在**任意新项目**上，能否自适应地建立门禁脚本？

### 8.1 结论：不能，P0 原方案只让"文档门禁"成立

| 门禁类型 | 自适应 | 缺口 |
|------|:---:|------|
| 文档类（编号/状态头/索引/归档） | ✅ | 逻辑与语言无关 |
| 命令类（tsc / go vet / mypy / clippy / lint / test） | 🟡 | 知识库有 Commands 可拼命令，但无"组织成门禁清单 + 装配"机制 |
| **脚本宿主选择**（Node/Python/make/shell） | ❌ | 原文仅一句风险提示"不能硬绑 Node"，无选择机制 |
| **领域门禁**（契约漂移 / 枚举一致 / 硬编码密钥 / DTO 白名单） | ❌ | "技术栈常见坑 → 可机检模式"映射知识完全缺失 |
| 装配点（pre-commit / pre-push / CI） | 🟡 | CI 已部分自适应；hooks 仅覆盖 JS（husky） |
| 门禁可跑性自测 | ❌ | 无"生成后实跑一次"步骤，可能产出立刻失败的检查 |

**风险**：在 Go/Python 项目上生成跑不起来的 `docs-check.mjs` + 引用 husky 的门禁，用户首日即删 → 反而损害可信度。

### 8.2 根因：缺三件东西

1. **门禁配方知识**（最大缺口）——源项目 11 个校验脚本 / 21 条门禁映射，由 **89 个真实 BUG 模式**磨出（**约 1/4 的缺陷模式最终固化为门禁**，其余多数不可机检或误报率高），无法凭空推理
2. **宿主选择规则**——脚本用什么跑 + Windows/Linux 双平台
3. **可执行性探测**——把项目已有命令（`package.json` scripts / Makefile targets / `pyproject [tool.*]` / CI 现成 job）转为门禁，而非凭空要求新装依赖

### 8.3 修法：门禁挂到已有知识库当第 4 段（不做新库）

现有每组件 3 段（实测 192 段落头 ≈ 64 条目）→ 增第 4 段：

```
## [组件名]
**Commands** / **Conventions** / **CI job** / **Gate**: 可机检红线 → 检查方式（命令 / 脚本要点 / 适用条件）
```

三层递进机制零改动即可产出门禁（精确命中取 Gate 段 / 命名启发取维度通用 Gate / 联网回退生成）。

另在「通用段落」补**跨语言门禁配方表**（语言无关，可立即撰写）：

| 通用红线 | 检查方式 | 跨语言等价 |
|---|---|---|
| 契约漂移 | 导出 schema + `git diff --exit-code` | OpenAPI / JSON Schema / protobuf / GraphQL SDL |
| 硬编码密钥 | 扫描 | gitleaks / trufflehog / 正则 |
| 锁文件一致 | 冻结安装 | `npm ci` / `--frozen-lockfile` / `go mod verify` / `cargo --locked` |
| 调试残留 | 禁用输出 | `no-console` / `grep print(` / go vet / checkstyle / clippy |
| 静态检查 | 编译器 | `tsc --noEmit` / `go vet` / `mypy` / `gradlew check` / `clippy -D warnings` |
| 格式化 | `--check` | prettier / `gofmt -l` / `black --check` / ktlint |
| 测试 + 覆盖率阈值 | 命令 + 阈值 | jest / vitest / pytest / `go test -cover` / jacoco |
| 迁移与模型一致 | 计数 / 命名比对 | 比对 migrations 目录与 schema 定义 |
| 文档一致性 | docs-check（语言无关） | 单脚本 + 任意宿主 |

### 8.4 宿主与装配自适应规则（建议写入 SKILL 新 Step 5.5）

**宿主（优先复用项目已有入口）**：① `npm run` / `make` / `tox` / `./gradlew` / `just` → ② 有 Node 用 `scripts/verify.mjs`（三平台通吃）→ ③ 有 Python 用 `scripts/verify.py` → ④ 均无用 `Makefile` 目标 `verify:` → ⑤ 兜底 `verify.sh` + `verify.ps1` 双份（成本最高，最后选）

**装配**：JS/TS → husky pre-commit + pre-push；Python → `pre-commit` 框架；Go/Java/Rust → Makefile / lefthook / CI；全语言 → CI 复用同一 verify 入口（本地与 CI 同语义）

**三条硬性要求**：① 只用项目已装工具，不得要求新装依赖 ② 生成后必须本地实跑一次，跑不通降级为"建议清单" ③ 分级 `blocking` / `warn`，存量项目默认全 warn 逐步升级

### 8.5 方案修正：P0-3 → P0-3'「门禁层生成器」

| 动作 | 内容 | 人工量 |
|---|---|:---:|
| ① 通用门禁配方表 | 进 `knowledge-base.md` 通用段落（§8.3 表） | 小（可立即写） |
| ② 组件 Gate 段 | 每组件第 4 段，~64 条 | **大（唯一重人工项）** |
| ③ 宿主 / 装配规则 | SKILL.md 新增 Step 5.5 | 小 |
| ④ hooks 扩语言 | Step 6.5 从"仅 husky"改为按语言选 | 小 |
| ⑤ 生成后自测 + 分级 | 进输出验收清单 | 小 |

**务实路径**：先做 ①③④⑤（通用配方表约 12 条即可覆盖多数项目 60–70% 门禁需求），②按实际遇到的组件逐批补——不阻塞发布，也不生成不可靠门禁。

> **关键判断**：要"在各种项目上都能建门禁"，决定性资产不是脚本本身，而是 **跨语言门禁配方表 + 组件 Gate 段**。

## 九、宪法层设计：门禁生长机制（2026-09-13 定案 · 方案 B 完整运行时）

> **设计前提**：门禁是**缺陷驱动的生长物**，不是初始化产物。
> 源项目实证：89 个缺陷模式 → 21 条固化门禁（约 1/4）；`check-agent-enum`（枚举不一致致保存必 500）、`check-weight-unit`（单位回退）、`check-numeric-dto`（缺省 query→NaN→SQL 500）**全部是踩坑之后才出现的**。
> 推论：初始化时项目无代码、无真实缺陷，只能产出"通用配方门禁"；**领域门禁必须由宪法层在开发过程中长出来**。

### 9.1 定位变化

| | 原设计 | 加宪法层后 |
|---|---|---|
| 交付物 | 一次性文件集 | 文件集 + **常驻生长机制** |
| 门禁来源 | Skill 初始化时生成（仅通用） | Skill 播**种子** + 项目自己的 AI **长出**领域门禁 |
| 对外叙事 | "我帮你生成工程化框架" | "**我让你的 AI 在开发中按宪法自动长出工程化能力**" |
| 随时间 | 衰减（文档漂移） | **增值**（门禁库 + 模式库累积） |

> 比喻：`knowledge-base.md` 的 `Gate` 段是**种子**（决定起点），宪法层是**生长激素**（决定上限）。缺种子第一天就没东西跑；缺宪法永远只有第一天的东西。

### 9.2 元规则（可直接落入 AGENTS.md，控制在 ≤15 行）

```markdown
## 门禁即规则（元规则，优先级最高）

1. **无门禁不立规** — 新增"阻断级"红线时，必须同时提交可执行检查并登记入
   `scripts/gates.json`；确实无法机检的红线，标注 `[无门禁]` 并写明原因。
2. **缺陷必闭环** — 每修复一个缺陷，必须判定"是否可机检"：可机检 → 新建或扩展门禁；
   不可机检 → 归入 `docs/B/B-04-BUG知识库.md` 模式。禁止只改代码不沉淀。
3. **契约唯一源** — 跨端字段以 DTO / schema 导出物为唯一事实源，导出物变更须随代码
   一同提交（CI 校验漂移）。

> **门禁清单唯一事实源**：`scripts/gates.json` ｜ **统一入口**：`scripts/verify.*`
> ｜ **宪法一致性校验**：`scripts/check-constitution.*`
> **开工前置**：读取 `scripts/gates.json`，了解本仓库现有门禁（避免重复踩坑）。
```

> 设计要点：元规则留在 AGENTS（短），**生长流程细则外链** `docs/B/B-06-门禁与工作协议.md`——防止宪法自身膨胀（源项目 AGENTS 已 294 行 > 自设 260 上限，即膨胀实证）。

### 9.3 门禁生长流程（6 步，写入 docs/B/B-06）

```
① 触发  修完一个缺陷 / 发现 AI 重复被纠正 / 新增了一条阻断级红线
   ↓
② 判定  四问（缺一不进）：
         可机检？  零新依赖（只用项目已装工具）？  真发生过或有明确证据？  误报率可控？
   ↓ 可机检 → 建门禁        ↓ 不可机检 → 只写规范 + 标 [无门禁] + 归入 B-04 模式
③ 生成  取配方：通用门禁配方表 → 组件 `Gate` 段 → 联网搜索（三层递进，与组件分类同机制）
   ↓
④ 注册  ① 写具体检查（scripts/checks/<id>.*）  ② 往 gates.json 追加一条（含 source / level / stage）
   ↓
⑤ 验证  负向验证：故意制造一次违规 → 确认门禁能拦住（拦不住则不得登记为 blocking）
   ↓
⑥ 登记  B-04-BUG知识库 新增/归类模式 + docs/B/B-06 记录 + CHANGELOG（如发版）
```

### 9.4 门禁清单单一事实源 `scripts/gates.json`

```json
[
  {
    "id": "docs-consistency",
    "source": "AGENTS#文档契约",
    "level": "blocking",
    "stage": ["pre-push", "ci"],
    "run": "node scripts/docs-check.mjs",
    "cwd": ".",
    "why": "文档漂移无人发现（源项目实测 18 篇缺状态头）"
  }
]
```

> 落地口径：`gates.json` 为**顶层数组**（本节初稿曾用 `{version, gates}` 对象包裹，实施时去掉外层包裹，避免多一层结构与"清单即数组"的校验代码绕弯）；权威结构以 `references/gates-templates.md` §一 为准。

- `verify` 入口**遍历清单**、按 `stage` 过滤执行、汇总耗时、任一步失败即退非 0
- husky / CI / Makefile **只引用同一入口**，不各自写命令 → 杜绝"脚本写了但没挂上"与三处漂移
- AI 新增门禁 = 写一个检查 + 清单加一条，装配自动生效

### 9.5 宪法一致性校验 `check-constitution`（把宪法自身纳入门禁）

| 校验规则 | 级别 |
|---|---|
| AGENTS 中标 `[门禁:<id>]` 或位于"阻断级红线"的条目 → `gates.json` 必须有对应 `source` | error |
| 标了 `[无门禁]` 但未写原因 | error |
| `gate.run` 引用的脚本/文件不存在 | error |
| 反向：`gates.json` 每条 `source` 必须在 AGENTS 中可定位（防僵尸门禁） | warning |
| `gates.json` 超过 N 条且警告级占比 > 50%（门禁只增不收敛） | info |

> **价值**：源项目的规则↔门禁映射表是**人工表格**且已漂移；改为机器校验后，宪法自己被约束——"宪法也要被门禁管"。

### 9.6 护栏（防止 AI 硬造脆弱门禁）

| 护栏 | 内容 |
|---|---|
| **准入门槛** | ① 可机检 ② 零新依赖 ③ 真发生过或有明确证据 ④ 误报可控 —— 缺一不进 |
| **命中率预期** | 现实约 1/4（89 模式 → 21 门禁）。**明确写入"不是每个坑都要门禁"** |
| **豁免治理** | 豁免须登记理由 + 设收敛目标（源项目 `allowed-*.json` 最终目标为零豁免） |
| **分级执行** | pre-commit 只跑快检查；pre-push 全量；CI 全量 + 重检查 |
| **新会话可发现** | 元规则含"开工前置读 gates.json"，否则新会话 AI 不知已有门禁，会重复踩坑 |
| **生成后实跑** | 生成的每个门禁必须本地实跑一次；跑不通降级为 `warn` 或"建议清单"，不做 blocking |

### 9.9 验收标准（可机检）

- [ ] 初始化后 `scripts/verify.*` 本地实跑**通过**（或全部为 `warn` 级）
- [ ] `check-constitution` 输出 **0 error**
- [ ] `gates.json` 条目 ≥ 1（至少 docs-check）
- [ ] **负向验证**：故意制造一次违规 → 门禁确实拦住（留证）
- [ ] 元规则章节 ≤ 15 行（防宪法膨胀）

### 9.10 风险与取舍

1. **生成物 +4~5**：对小型项目是负担 → 按规模阈值触发（低于阈值只生成"docs-check 单条门禁 + 统一入口"，不生成 checks/ 与协议文档）
2. **宪法膨胀**：元规则必须短（≤15 行），细则一律外链
3. **AI 造脆弱正则**：靠准入门槛 4 条 + 生成后负向验证兜住
4. **门禁只增不收敛**：靠 `check-constitution` 的 info 提示 + 豁免收敛目标治理（源项目 `allowed-*.json` 从 7 条收敛到 0 即先例）
