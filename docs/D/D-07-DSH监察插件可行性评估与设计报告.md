## 一、结论速览

| 待答问题 | 结论 |
|---|---|
| **能不能做** | 能。DSH 的扩展点逐个对得上需求，且官方插件 `dsh-agent-instructions` 已有同类型接线先例（观察 `tools/result` 中的一手 `read`/`write`/`edit`） |
| **痛点真不真** | 真，且有学术实证（北大 RepoComplianceBench、ETH SRI 两篇论文），非主观推断 |
| **有没有直接竞品** | 有，且是一条已成型赛道（多个 3 万–18 万 star 项目）。但**存在一格真空**：无人做「过程合规」与「规范体系自身的健康度」 |
| **值不值得做** | 值——**前提是把形态从"全面工作台"收缩为"旁挂只读监察员"**。原形态（大而全观测台）命中已知高失败品类 |
| **最大风险** | ① 误报率（生死线）② 被官方吸收（通用能力已被占位过）③ 范围失控 ④ DSH developer preview 破版 |
| **本文档的目的** | 固化已收敛的定位与设计，并**保留被否方案的否决理由**（见第五节，其价值高于结论本身） |

**一句话结论**：这条路的成立与否不取决于技术，而取决于**形态取舍**——做"全面"会死，做"深"能活。

## 二、从原始诉求到最终定位（8 轮收敛）

| 轮次 | 原始想法 | 澄清后的判定 | 关键否决点 |
|---|---|---|---|
| 1 | 把项目能力做成编程平台插件，先适配 DSH | 方向成立；但**已有的 `dsh-plugin/` 只是"把技能装进去"（被动知识）**，与设想的"主动执行层"差一个量级 | — |
| 2 | 插件要"实时掌握项目情况、及时发现问题" | 成立；对应 DSH 的 `systemPrompt.context()` + `tools/post-execute` | — |
| 3 | 独立的可视化窗口 + 自有 Agent 盯梢 + 读全部对话/提交记录 + 实时项目结构图到每个调用 | **形态过重**；判定为"一台平台而非一个插件" | 调用级/管线级实时图**原理上不可实现**（见第五节 N-5） |
| 4 | 做"整合协同的流程闭环工作台" | 战略直觉正确（整合层是历史赢家位置），**但命中已知高失败品类**（IDP/开发者门户） | 见第四节 4.3 |
| 5 | （修正）不是工作台，是**旁挂的分支能力**：只检测、只看着、给建议、用户点击采纳 | **形态成立**。工作流零改动 + 判定根扎自有数据 + 被动旁挂不需推广 | — |
| 6 | 判定应围绕 README 与规范文档；误报要记录学习；行为层要监控（超大文件/不做模块化/重复造轮子） | **行为层监控是全篇最准的一击**；但 README 的角色需拆分为「画像输入」而非「判定依据」 | 见第五节 N-8 |
| 7 | 所有项目都要先用 SKILL 初始化，我们才有依据 | 与第 4 步定下的"B 外壳"策略冲突；改为**一键初始化 + 分层降级** | 见第五节 N-10 |
| 8 | 初始化由谁执行 | **插件递条子，agent 执行**——统一了"只读契约 / 初始化 / 豁免"三件原本冲突的事 | 见第五节 N-7 |

## 三、可行性对账（DSH 扩展点）

DSH 采用 Cordis「一切皆插件」架构，产品内无特权核心，插件与官方插件地位平等。

| 需求 | DSH 扩展点 | 判定 |
|---|---|---|
| Agent 侧可调用的检测入口 | `ctx.tools.register(defineTool(...))` | ✅ 现成 |
| 用户侧状态面板（"看到项目是否健康"） | Client 半侧 `lib/client.js` + `ctx.slots.inject`（React） | ✅ 现成，但**必须走 Client 半侧** |
| 改完即查（过程监控） | `ctx.on('tools/post-execute')` 观察工具结果 | ✅ 已由官方插件验证接线可行 |
| 拦截/审批（本设计**不使用**） | `ctx.on('tools/pre-execute')` 可返回 `ask` | ⛔ 主动不做（违背只读承诺） |
| 会话首步注入基线（本设计**不使用**） | `ctx.on('agent/pre-step')` | ⛔ 让给官方插件（见第五节 N-3） |
| 后台长任务 | `ctx.jobs.start({...})`（勿自起线程） | ✅ 现成 |
| 动态上下文快照（按需，非高频） | `ctx.systemPrompt.context()`（仅变化时进历史） | ✅ 现成 |
| 只读文件访问 | 可选依赖 `ctx.get('fs')`（不硬 `inject`，无 provider 时降级为 no-op） | ✅ 现成 |
| 提交记录 | `git log/diff/show` 只读子进程（已评估并接受，见 6.2） | ⚠️ 唯一破例项 |

> **技术风险提示**：`tools/post-execute` 比现有插件的 `skills.registerProvider` **深得多**。DSH 仍处 developer preview（已记录 rc.8 → 0.1.1-rc.2 → 0.1.2-rc.1），采用越深的扩展点，破版时受损越快。这是选这条路的固有成本。

### 4.2 关键实证数据（痛点真实性）

| 证据 | 内容 | 对本项目的意义 |
|---|---|---|
| 北大 RepoComplianceBench（arXiv:2607.26819） | 49 仓库 / 106 任务 / 四个前沿模型：**coding agent 几乎从不主动检索仓库的贡献规则**；提醒、规则引用、验证器反馈可救回"披露"与"验证"；**禁止类与人工升级在任何条件下均测不通** | 直接证明"规则写在文件里无效"，且证明**过程监控是唯一还开着的口子** |
| ETH SRI（arXiv:2602.11988） | SWE-bench Lite 上：LLM 自动生成的 context file **平均降低 3% 成功率、增加 20% 推理成本**；手写的也仅约 +4%；判据是"agent 自己读代码能发现的就不该写" | 静态 context file 的天花板就在此；"规范可执行化"是正确的延伸方向 |
| MCP 上下文成本 | 连接 3 个 MCP Server，仅工具定义可能占用约 14.3 万 token（200K 模型的 72%） | **碎片化在 AI 时代加剧而非缓解**——这是"整合"的真实技术缺口 |
| Platform Engineering / IDP（2026） | 80–90% 企业已建 IDP，**平均内部采用率仅 10%**；**近 70% 在 18 个月内交付不出 ROI**；头号挑战是"开发者采用"（45.3%），远超技术挑战；Backstage 占 89% 份额 | 见 4.3 判定依据 |
| Backstage DIY 复盘案例 | 4 名平台工程师全职 9 个月，200 名开发者，周活从 15% → 12% → 8% → 5% → **3%**。失败的四条（服务目录 / 文档集中 / 脚手架模板 / 部署仪表盘）恰是同类产品的典型设计 | **反面教材：门户类形态的标准死法** |
| 行业数据 | 90–95% 的 AI 编码项目无法从试点进入生产；超六成企业认为 AI 代码满足不了生产可维护性 | 需求侧的宏观支撑 |

### 4.3 判定：为什么"全面工作台"会死，而"旁挂监察员"能活

| IDP 失败机制 | 旁挂监察员形态 |
|---|---|
| 要求开发者**改变工作流**去使用门户 | 用户照常干活，**工作流零改动** |
| 建"单一玻璃面板"，聚合他人输出 | 判定根扎在**自有规范数据**（宪法 / 门禁覆盖率 / 规范↔门禁映射） |
| 需推广、培训、变更管理（45.3% 卡在此） | 被动旁挂，**不需推广** |
| 用插件数量堆功能，造成**认知过载** | 只输出"哪里不健康" |
| 维护门户吃掉全部产能 | 单一检测引擎，无门户可维护 |

**关键差异只有一条：IDP 要求用户搬家，本设计只要求用户允许被观察。** 门槛差一个数量级。

## 五、被否掉的方案与否决理由（本文档核心价值）

> 以下每条都是"看起来更诱人但被否掉"的选项。**理由比结论值钱**——实施阶段最需要的正是"为什么当初没选那个更明显的路"。

| # | 被否方案 | 否决理由 |
|---|---|---|
| N-1 | 大而全的「项目实时观测台」（采集 / 分析 / 聚合 / 展示 / 子 Agent 五层） | ① 每层都有更强现成项目（3 万–18 万 star）② 单人 vs 团队/公司量级 ③ 范围不可控 ④ 命中 IDP 高失败品类 |
| N-2 | 独立可视化窗口 + 自有 Agent 常驻盯梢 | 常驻 Agent 的 token 成本会烧穿，且 90% 唤醒无意义。**必须"规则过滤在前，Agent 在后"** |
| N-3 | 做 L1「指令注入 / AGENTS.md 实时化」 | 官方插件 `dsh-agent-instructions` 已占（含嵌套文件发现 + 变更/删除上报）。硬碰无意义 |
| N-4 | 把仓库既有判定逻辑第三次内联进插件 | 违反 AGENTS.md 的**「契约唯一源」元规则**（现已有 `references/*.mjs` 与 `scripts/` 两处）。当前决策：两份实现 + golden case 一致性门禁；若做平台无关内核则可回归唯一事实源 |
| N-5 | 实时、全量、细化到每个调用与逻辑管线的项目结构图 | **原理上不可实现**：语言无关的精确调用图不存在（动态分派 / 反射 / DI 容器 / 路由表）。降级路径：import 级依赖图 → 变更驱动重算 → 调用级按需下钻 |
| N-6 | 用 shell 调用项目自带门禁脚本（`node scripts/verify.mjs`） | 与只读契约冲突（执行任意代码）。改为插件内置只读检查 |
| N-7 | 插件直接执行初始化（自己写 `AGENTS.md` / `docs/` / `gates.json`） | **打破只读契约**。改为「插件递条子，agent 在 DSH 原生审批路径下执行」 |
| N-8 | 把 `README.md` 当判定依据 | README 是对外介绍、经常改、且**本不该承载规范**（与 ETH 论文结论一致）。拆分为：判定依据 = `AGENTS.md` 规范章节 + `gates.json`；README = **画像输入** |
| N-9 | 把误报处理成"这个模式以后不再报" | 这是用**降低召回换精确度**，会放过真违规（比误报更危险）。正确做法：规则错 → 收窄条件；本次判错 → 加例外 |
| N-10 | "所有项目必须先用 SKILL 初始化才有依据" | 与「B 外壳 + A 内核（零配置可跑）」直接冲突，且"要求用户先做准备工作"是采用率断崖的标准机制（IDP 10% 采用率为证）。改为**一键初始化 + L0/L1/L2 分层降级** |
| N-11 | 插件自己记误报豁免（本地隐形状态） | 团队不一致、不可 review、换机器即丢。改为**生成可提交条目**，使豁免成为可版本化的项目资产 |
| N-12 | 自动推断画像并静默放宽宪法（如"看起来像演示项目，我自动放宽"） | **静默放宽 = 用户不知道自己在裸奔**。必须显式声明 + 面板可见 + 豁免须写原因（复用 `check-constitution.mjs` 规则 D 的现成实现） |
| N-13 | 工具拆成 `check_gates` / `check_docs` / `check_drift` / `check_version` 多个 | 工具集膨胀且模型需猜该调哪个；awesome 目录会核对描述中的工具数量。改为**单入口 + `scope` 参数** |
| N-14 | 第一版就做完整 UI + 全部检查项 | ① UI 会让误报显得更严重 ② 范围失控。改为**判定引擎 + 纯文本输出**先行，只为验证准确率与误报率 |

## 六、设计卡

### 6.1 定位与纪律

**一句话定位**
> 一个只读的项目监察员：坐在 DSH 旁边看着 agent 干活，顺手给项目体检；发现问题递条子，要不要治你说了算。

**贯穿全部设计的一条纪律**
> **永不动手，只递条子。初始化是条子，豁免也是条子。**

因为这一条，"只读契约"、"初始化"、"误报闭环"三件原本互相冲突的事得以统一。

### 6.2 权限契约

```
Filesystem read   yes — your project (AGENTS.md / docs/ / gates.json)
Filesystem write  $DSH_HOME only — never your project
Child processes   git read-only (log / diff / show) only
Network           no
```

> ⚠️ **诚实性要求**：awesome-dsh-plugin 会拿一行描述对照源码核对。README 中不得宣称 `write: no`——状态与统计确会写入 `$DSH_HOME`。诚实且精确的画像反而是信任货币。

### 6.3 输入契约（两个用途必须分开）

| 来源 | 用途 |
|---|---|
| `AGENTS.md` 强制规范章节 + `gates.json` | **判定依据**（可机检的规范条目 = 唯一事实源） |
| `README.md` / `package.json` description / 目录结构 / 依赖清单 / git 历史 | **画像输入**（这是个什么项目） |

### 6.4 能力分层（把"前提"变成"升级路径"）

| 层 | 触发条件 | 判定能力 |
|---|---|---|
| **L0** | 任何项目，零配置 | 超大文件、重复造轮子（外部依赖）、文档契约有无 |
| **L1** | 探测到 `AGENTS.md` 规范条目 | 文档体系、宪法一致性、门禁覆盖 |
| **L2** | 探测到 `gates.json` 契约 | 宪法↔门禁双向映射、门禁有效性、规范漂移 |

### 6.5 检查项（★ 为差异点）

| 类型 | 检查项 | 依据来源 | 可行性 |
|---|---|---|---|
| 静态 | 文档契约状态头 / 编号连续性 / 体积 | `docs-check.mjs` | ✅ 有现成实现 |
| 静态 | 宪法一致性（规则 A–D） | `check-constitution.mjs` | ✅ 有现成实现 |
| 静态 | 门禁覆盖率、门禁有效性、规范漂移 | `drift-check.mjs` + `gates.json` | ✅ 有现成实现 |
| **★过程** | **超大单体文件**（阈值按画像分档） | 行为观察 | ✅ 确定性 |
| **★过程** | **重复造轮子（外部）**：新增函数 vs 已装依赖导出名相似度 | 行为观察 + 依赖清单 | ✅ 相当可行 |
| **★过程** | **不做模块化**：新增代码是否落在既有模块边界内 / 单文件导出数 / 跨模块耦合度 | 行为观察 | ⚠️ 需先定义口径 |
| **★过程** | 硬编码 / 死代码（画像相关，demo 允许） | 行为观察 + 画像 | ✅ |

> **差异点说明**：生态内所有工具（CodeRabbit / Drift / CodeGraph）都在做**结果合规**；本设计的 ★ 项做的是**过程合规**——看 AI 正在新增的代码。其独特之处在于：**agent 永远不会自己举报自己违规**，此信息只对旁挂观察者可见。

### 6.6 画像与豁免

- 画像**显式声明**（如 `profile: demo`），**可见、可被用户覆盖**
- 放宽的对象是**判定规则**，**不是宪法条文**——条文仍在，只是降级为 `info`
- 面板必须显示：`当前按 demo 画像运行 · 以下 N 条规范已豁免`
- 豁免须**显式 + 写明原因**（直接复用 `check-constitution.mjs` 规则 D 的现成判定）

### 6.7 误报闭环

- 豁免**生成可提交条目**递给用户（插件不写项目）→ 豁免成为可 review / 可版本化 / 团队共享的项目资产
- 状态与历史写 `$DSH_HOME`
- 误报须**分两种情况处理**：规则错 → 收窄条件；本次判错 → 加例外。**绝不用降低召回换精确度**
- 误报数据 → 人工确认 → 进规则库（复用 v1.8.0「缺陷必闭环」机制，但不允许插件自动改自身规则）

### 6.8 双面结构

| 面 | 面向 | 机制 |
|---|---|---|
| Agent 面 | 正在干活的 agent | `blueprint_check` / `blueprint_init` 工具 |
| 人面 | 用户 | Client 半侧面板：状态 + 一键初始化 + 点击采纳 |

### 6.9 采纳的三种方式

1. 复制提示词
2. 在 DSH 起新任务治理
3. 一键初始化（首次）

## 八、最小可信版本与实施顺序

**最小可信版本（够了就停）**

> 3 条检查（超大文件 + 重复造轮子 + 门禁有效性） + 画像（demo / prod 两档） + 豁免（可提交条目） + 误报闭环

**实施顺序**

1. **判定引擎 + 纯文本输出**（无 UI）→ 只验证一件事：**准确率与误报率**
2. 跑在自己仓库上（真实靶子：2 条种子门禁 + `docs/D` 契约 + 刚修过的口径漂移）
3. **准了再做 Client 面板**；不准就调检查项，别在 UI 上花时间

> 理由：**UI 会让误报看起来更严重**。文本框里的误报，用户想"算错了吧"；仪表盘上的红色警告，用户想"这工具不行"。

**成功判据（可证伪）**

| # | 判据 |
|---|---|
| 1 | `dsh --profile web --dump-config` 可见监察员插件行 |
| 2 | 会话中模型**未被点名**即可发现并调用 `blueprint_check` |
| 3 | 故意制造漂移（如 `gates.json` 的 `run` 指向不存在的文件）→ 改完文件后监察员**主动**报出 |
| 4 | 恢复现场 → 报告消失 |

> 判据 3、4 才是价值证明（**能造出问题、也能消掉问题，且不依赖模型自觉**）；判据 2 只证明接线正确。

## 九、风险清单

| # | 风险 | 应对 |
|---|---|---|
| R-1 | **误报率**（检查类工具的容忍度是周级：连续误报一周即被关闭且不再打开） | 每条建议必须自带四件套：**证据（文件:行）/ 依据（指回规范条目）/ 动作（采纳后做什么）/ 置信度**。铁律：**宁可不报，不可误报**；判不准降级为 `info` |
| R-2 | **被官方吸收**（`dsh-agent-instructions` 即官方下场先例） | 护城河挖在**语义模型**（宪法 / 门禁口径 / 规范↔门禁映射）而非通用能力；通用能力必然被吸收 |
| R-3 | **范围失控**（已累积 8 个模块） | 最小版本只碰 4 个；其余全部后置 |
| R-4 | **DSH 破版**（developer preview，采用 `tools/post-execute` 比现状更深） | 薄宿主适配 + 厚可迁移内核；接受这是固有成本 |
| R-5 | **画像判错导致判定全错** | 画像必须可见、可覆盖、可显式声明 |
| R-6 | **判定口径漂移**（半年后无人知道某检查为何存在） | 规范条目 ↔ 检查项必须建立映射；复用 `gates.json` 的 `why` 字段模式 |
