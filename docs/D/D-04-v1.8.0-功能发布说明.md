## 一、本次更新一句话

**把 Skill 从「规范生成器」推进到「规范执行器 / 生长器」——初始化时只播种通用门禁，项目的 AI 在开发中按宪法层元规则，把真实踩过的坑长成领域门禁。**

v1.7.x 解决的是「规范写得出来」，v1.8.0 解决的是「规范**管得住、活得下去**」。

## 二、为什么做这次更新

v1.8.0 之前，本 Skill 强在**规范层**（Step 2 拼接 + `code-conventions.md` + `ai-common-mistakes.md`），但**流程层与校验层基本空白**：

| 缺口 | 影响 |
|------|------|
| 生成的规范全是「写在文档里的约定」，没有任何机器可执行的检查 | 红线靠自觉，AI 违规无人拦，规范退化为参考文档 |
| 初始化时项目无代码、无真实缺陷，注定只能产出通用规则 | 领域红线（字段枚举一致、单位统一等）无处生长 |
| 没有「缺陷 → 门禁」的沉淀机制 | 同一个坑反复踩，规范体系"只生不长" |

**源项目实证**（详见 [D-03-真实项目文档体系优化引入评估报告.md](D-03-真实项目文档体系优化引入评估报告.md) §九）：一个真实项目跑出了 **11 个校验脚本 / 21 条门禁映射**，它们由 **89 个真实缺陷模式**磨出（约 **1/4 固化率**）；其中 `check-agent-enum`、`check-weight-unit`、`check-numeric-dto` **全部是踩坑之后才出现的**。

**结论**：门禁是**缺陷驱动的生长物**，不是初始化产物。因此本次引入**宪法层**——由 `AGENTS.md` 的元规则约束 AI，在开发过程中把领域门禁长出来。

## 三、核心更新

### 3.1 宪法层元规则（写入生成的 AGENTS.md）

三条元规则（章节总长 **≤ 15 行**，细则一律外链，防止宪法自身膨胀）：

1. **无门禁不立规** — 新增阻断级红线必须同时提交可执行检查并登记入 `scripts/gates.json`；确无法机检的标注 `[无门禁]` 并写明原因
2. **缺陷必闭环** — 每修复一个缺陷必须判定「是否可机检」：可机检 → 新建/扩展门禁；不可机检 → 归入 BUG 知识库模式。禁止只改代码不沉淀
3. **契约唯一源** — 跨端字段以 DTO / schema 导出物为唯一事实源，导出物变更须随代码一同提交

并配套**开工前置**：AI 新会话先读 `scripts/gates.json`，了解本仓库现有门禁，避免重复踩坑。

### 3.2 门禁生长流程（6 步）

```
① 触发  修完缺陷 / AI 重复被纠正 / 新增阻断级红线
   ↓
② 判定  准入门槛四问（缺一不进）：可机检？ 零新依赖？ 真发生过？ 误报可控？
   ↓ 可机检 → 建门禁        ↓ 不可机检 → 只写规范 + 标 [无门禁] + 归入 BUG 模式
③ 生成  三层递进取配方：跨语言门禁配方表 → 组件 Gate 段 → 联网搜索
   ↓
④ 注册  ① 写具体检查（scripts/checks/<id>.*） ② gates.json 追加一条
   ↓
⑤ 验证  负向验证：故意制造一次违规，确认门禁能拦住（拦不住不得登记为 blocking）
   ↓
⑥ 登记  BUG 知识库 + 协议文档 + CHANGELOG
```

四问的用意：**可机检**（靠人主观判断的红线强做只会假绿）、**零新依赖**（要新装工具用户就会绕过）、**真发生过**（凭想象设防会堆出死门禁）、**误报可控**（高频误报会被 `--no-verify` 绕过，宁可降 `warn`）。

> 现实预期：真实工程中约 **1/4** 的缺陷模式最终固化为门禁，**不是每个坑都要门禁**。

### 3.3 门禁清单唯一事实源 + 统一入口 + 宪法自校验

| 生成物 | 作用 |
|--------|------|
| `scripts/gates.json` | 门禁清单唯一事实源，字段 `id / source / level / stage / run / cwd / why` |
| `scripts/verify.*` | 统一入口，遍历清单执行，支持 `--stage=pre-commit\|pre-push\|ci`，`blocking` 失败退出非 0 |
| `scripts/check-constitution.*` | 宪法自校验，`AGENTS.md` 红线 ↔ 门禁清单**双向比对**：红线缺门禁 = error，僵尸门禁 = warning |

**关键收益**：新增门禁 = 「写具体检查 + 清单追加一条」，pre-commit / pre-push / CI 通过同一入口自动生效，**不会再出现「脚本写了但没挂上」**。

### 3.4 门禁配方知识（知识库升级）

- `references/knowledge-base.md` 通用段落新增**跨语言门禁配方表（10 条）**：契约漂移 / 硬编码密钥 / 锁文件一致 / 调试残留 / 静态检查 / 格式 / 测试覆盖率 / 迁移与模型一致 / 文档漂移 / 单文件过大，每条含「通用红线 / 检查方式 / 跨语言等价」三列
- 组件条目格式由 **3 段升级为 4 段**（`Commands` / `Conventions` / `CI job` / **`Gate`**），首批 **12 个高频组件**补齐 `Gate` 段（可机检红线 → 检查方式）
- 收益：Go / Python / Java / Rust 项目取的是 `go vet` / `mypy` / `gradlew check` / `cargo clippy` 等价检查，而不是产出跑不通的 Node 脚本

### 3.5 新增 Step 5.5「门禁装配」

规则写在 `AGENTS.md`、清单生成于 Step 3.5，**Step 5.5 把它们接到提交与 CI 的触发点上并实跑验证**：

- **宿主降级选择**：项目已有入口（`npm run` / `make` / `tox` / `./gradlew` / `just`）→ Node → Python → `Makefile` → shell 双份
- **装配点**：JS/TS 用 husky（pre-commit 只跑快检查，pre-push 跑全量）/ Python 用 `pre-commit` 框架 / Go·Java·Rust 以 Makefile + CI 为主入口；**全语言 CI 必须复用同一 `verify.*` 入口**（本地与 CI 同语义）
- **五条硬性要求**：零新依赖 / 生成后必须实跑 / 新 `blocking` 门禁须负向验证 / `blocking` 与 `warn` 分级（存量项目默认全 `warn`）/ 豁免须登记理由并设收敛目标
- **输出**：宿主 / 装配点 / 实跑结果 / blocking 与 warn 条数，实跑输出作为证据留档

### 3.6 文档契约 + `docs-check` 校验脚本（首个门禁种子）

- **文档契约**：B / C 系列文档须带状态头 `> 版本: … | 更新: … | 状态: …`；编号唯一（缺号须有归档或索引标注）；索引覆盖全部非归档文档；单篇超限须拆分
- **`references/docs-check.mjs`**：校验编号连续性 / 状态头 / 索引覆盖 / 归档冲突 + 单文件体积，输出分级 **error（阻断）/ warning（不阻断）/ info（提示）**，退出码 0 = 无 error
- 存量债不阻断：已有项目的历史文档不达标记为 warning，新增即达标、存量逐步补

### 3.7 AI 编程工作协议

- **7 步任务生命周期**（不可跳步）：读规范 → 查先例 → 定契约 → 列计划 → 实施 → 跑门禁 → 回写文档
- **证据标准**：代码改动给 `文件:行号`，验证给「命令 + 实际输出」；无法验证须显式标注「未验证 + 原因 + 风险」；**禁止**用「应该没问题 / 看起来对 / 理论可行」替代证据
- **DoD 8 条** + **违规处理表**（未跑门禁即声明完成 → 视为未完成，退回第 6 步）+ **缺陷复盘模板**
- 生成物：`docs/B/B-06-门禁与工作协议.md`（按需）

### 3.8 按规模阈值触发（避免过度工程）

小型项目（源码文件少 / 单人开发）只生成**「单条门禁（docs-check）+ 统一入口」**，不生成 `scripts/checks/` 目录与协议文档；中大型项目才生成完整门禁层。

## 四、使用方式

| 场景 | 行为 |
|------|------|
| 新项目初始化 | 获得宪法层元规则 + 门禁清单与统一入口 + 文档契约与校验脚本；初始化即播种通用门禁，领域门禁由开发中生长 |
| 已有项目接入 | 增量路径不变：只补缺失，不覆盖已有配置；门禁默认全部为 `warn`，稳定后逐步升级为 `blocking` |
| 日常开发 | AI 按协议 7 步走；门禁在 pre-commit / pre-push / CI 同一入口执行；缺陷修复后按 6 步生长流程判定是否补门禁 |

## 七、已知限制与后续方向

- 组件的 `Gate` 段**未一次性补全**（70+ 组件中首批 12 个高频组件）——多数组件尚无真实踩坑依据，凭想象补 Gates 会堆出死门禁；其余按实际遇到的组件逐批补
- 面向具体语言的完整 `check-*.mjs` 领域脚本库**不预置**——领域强绑定，由使用方项目按生长流程自行长出
- 门禁生长速度取决于项目实战频率与 AI 是否遵守元规则
- 后续可考虑：把 `docs-check.mjs` 移植为 Python / shell 等价实现，覆盖更多宿主
