这是什么

给第一次听说这个项目的朋友，30 秒背景

Project Blueprint 是一个开源的 AI Agent 技能包 —— 一句话让任何项目具备 AI 开发能力。

它不是静态模板，而是一个自主发现引擎：扫描你的项目文件 → 智能推断技术栈 → 从 70+ 组件知识库实时拼装。所以你拿到的 AGENTS.md 源自项目的真实技术栈，不是换了个名字的通用模板。

解决的问题也很具体：AGENTS.md 已是行业标准（60,000+ 开源仓库在用），Anthropic 内部基准显示有它的项目可减少 40–60% 的「错误模式重写」；但手写一份高质量的通常要花半天到一天，而且每个新项目都得重来一遍。

你只需说一句「初始化这个项目的开发规范体系」，它会把下面这些一次性交给你的项目：

AGENTS.md 开发规范 · 按真实技术栈生成
docs/ 文档骨架 · A/B/C/D/E 五级分类
多 IDE 适配 · CLAUDE.md / .cursor/rules / Copilot 指令
CI/CD 流水线 · GitHub Actions / Gitee Go
Git 规范 + CHANGELOG · 分支策略与提交格式
测试制度 · 按项目阶段分层，不硬塞示例
基础代码规范 + AI 高频错误清单 · 6 类 + 27 条
门禁层 · 清单唯一源 + 统一入口 + 宪法自校验
MCP 工具推荐清单 · 按探测到的技术栈匹配

支持 Claude Code、Cursor、GitHub Copilot、Codex、Windsurf、OpenCode、DeepSeek Harness 等 28+ 工具；已有项目只补缺失、不覆盖已有配置。安装见文末。

为什么做这两个版本

AI 编程真正的短板不是「写不出代码」，而是「写的代码没人守规矩」

而「把规矩写进 AGENTS.md 就完事」这条路，已经被研究证明效果有限：

规则根本没人读
不主动读规则
coding agent 极少主动去读仓库里的贡献规则；提醒与验证器反馈能救回「披露」和「验证」，但「禁止类」规则在任何条件下都测不通。
北大 RepoComplianceBench · 49 仓库 / 106 任务 / 四个前沿模型
自动生成的规范反而拖后腿
-3% 成功率
+20% 成本
LLM 自动生成的 context file 平均降低任务成功率、增加推理成本；判据是「agent 自己读代码能发现的，就不该写」。
ETH SRI · SWE-bench Lite 实证
规范写完就烂在那里
58% 只有一次提交
agent 配置文件的修订率仅 0.4 commits/月 —— 说明规范一旦不可机检，就没有人会去维护它。
10,008 仓库实证
结论：规范必须可机检、能拦住动作，否则它就只是一份参考文档。这两个版本就是沿这条线走的——v1.8.0 让规范管得住，v1.9.0 让规范铺得开、不跑偏。

v1.8.0 — 宪法层与门禁生长机制

把门禁从「初始化一次性产物」升级为「宪法驱动的生长物」

三条元规则（写入生成的 AGENTS.md）

无门禁不立规
新增阻断级红线，必须同时提交可执行检查并登记入 gates.json；确实无法机检的标注 [无门禁] 并写明原因。
缺陷必闭环
每修一个缺陷必须判定「是否可机检」：可机检 → 新建 / 扩展门禁；不可机检 → 归入 BUG 知识库模式。禁止只改代码不沉淀。
契约唯一源
跨端字段以 DTO / schema 导出物为唯一事实源，导出物变更须随代码一同提交。

门禁生长 6 步

  1. 触发
    修完缺陷 / AI 重复被纠正 / 新增阻断级红线
  2. 判定 — 准入门槛四问，缺一不进
    可机检？零新依赖？真发生过？误报可控？
  3. 生成 — 三层递进取配方
    跨语言门禁配方表 → 组件 Gate 段 → 联网搜索
  4. 注册
    写具体检查 + gates.json 追加一条
  5. 验证 — 负向验证
    故意制造一次违规，确认门禁能拦住；拦不住不得登记为 blocking
  6. 登记
    BUG 知识库 + 协议文档 + CHANGELOG

四问的用意：可机检（靠主观判断的红线强做只会假绿）、零新依赖（要新装工具用户就会绕过）、真发生过（凭想象设防会堆出死门禁）、误报可控（高频误报会被 --no-verify 绕过去，宁可降 warn）。

配套三件套

生成物作用
scripts/gates.json门禁清单唯一事实源（id / source / level / stage / run / cwd / why）
scripts/verify.*统一入口，支持 --stage=pre-commit|pre-push|ci，blocking 失败退出非 0
scripts/check-constitution.*宪法自校验：AGENTS.md 红线 ↔ 门禁清单双向比对，红线缺门禁 = error，僵尸门禁 = warning

关键收益：新增门禁 = 「写检查 + 清单追加一行」，本地与 CI 走同一入口，不会再出现「脚本写了但没挂上」。

一个真实数据

真实缺陷模式
89 个
来自一个真实项目的生产实践沉淀
最终固化为门禁
21 条
约 1/4 固化率——不是每个坑都要门禁，这符合现实预期

其中「字段枚举一致」「重量单位统一」「数值型 DTO」这几条红线，全部是踩坑之后才出现的。这就是「门禁是生长物，不是初始化产物」的实证。

v1.9.0 — 跨栈通用性与规范不漂移

技能正文瘦身为按需加载，多子项目按官方就近原则生成，漂移变成可机检事件

技能正文瘦身 · 常驻上下文直降
1012 → 113 行
7 个 Step 细节迁出为按需加载文件；78 个标题 100% 可定位，内容零丢失
知识库覆盖面
16 维度 · 95 组件
新增 AI/LLM 栈、IaC 与云原生、可观测性、数据工程、原生移动 5 个域

另外三件关键更新

Monorepo 嵌套 AGENTS.md
多子项目（≥2 个构建/清单文件）不再把各包规范塞进根单文件，改为「根文件 = 全局约束 + 子项目索引」+「各子项目目录下的包级 AGENTS.md」，对齐官方就近原则（closest-file-wins）。单项目场景行为零变化。
规范漂移门 · 第二条种子门禁
把「代码/依赖 ↔ 规范」的不一致做成可机检事件：依赖清单变了但技术栈行没更新 → warning；模块速查表与实际目录对不上 → warning；gates.json 引用的脚本已删除（僵尸门禁）→ error。
顺手自吃狗粮
本仓库此前门禁是「假绿」——检查因目录不存在被整块跳过。现已修复校验范围自适应，并为自己建起 scripts/ 门禁层。

另附：规范驱动开发六阶段（specify → plan → tasks → checklist → implement → verify，checklist 的可机检项可直接注册为门禁）、工具私有增强层（Cursor glob 分层 / Claude Code hooks·subagents / Copilot 分层，并附防漂移条款）、量化评估基准。
