# D-09 机制可发表性交叉验证报告

> 版本: v1.0 | 更新: 2026-09-18 | 状态: 已完成
> 验证对象：本项目核心机制（门禁生长棘轮 / 规范即可执行检查 / 宪法层 / 规范漂移门）的「可发表性」论断
> 方法：将机制拆为可命名的技术命题，逐条对撞公开文献（arXiv 预印本 / 行业署名文章 / 竞品仓库），判定**概念新颖性**与**评估完备度**两件事

***

## 一、结论

1. **概念层不新颖**：「每次 AI 犯错就固化一条永久规则」已被行业正式命名（the ratchet principle），且已有至少 4 篇论文覆盖其变体，其中 2 篇自带评估。
2. **实现层仍属工程扎实，但已非最早**：截至 2026-09，自动化演化 harness 组件的闭环实现与量化评估已被 arXiv 2604.25850（2026-04）完成并超越。
3. **评估层是致命缺口**：本项目只有 1 条单项目经验（89 缺陷模式 → 21 条门禁，≈1/4 固化率），无 baseline、无对照、无复发率度量、无用户研究——这是「不能作为机制类论文投稿」的决定性原因。

> **可发表形态**：经验/案例类短文（ICSE-SEIP / FSE-IVR / ASE industry track，或先挂 arXiv 预印本），主题收敛为「**在零新依赖约束下，哪些缺陷值得可机检化——判定程序 + 真实固化率实证**」，而**不是**「我们提出了一种新机制」。

***

## 二、机制拆解与对撞结果

| # | 本项目机制 | 已存在的公开工作 | 判定 |
|---|---|---|---|
| 1 | 「每次 AI 犯错就固化一条检查」的棘轮闭环（门禁生长 6 步） | **Addy Osmani《Agent Harness Engineering》(2026-04-19)** 命名 **the ratchet principle**：「anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again」「constraints are added only when real failures happen, and removed only when a capable model renders them obsolete」 | ❌ 原则已被命名，非本项目首创（D-05 §二.2 已自行承认「业界刚命名」） |
| 2 | 门禁/规范随失败自动生长，且可审计、可回滚 | **arXiv 2604.25850《Agentic Harness Engineering》(v1 2026-04-28 / v4 2026-05-18)**：闭环自动演化 harness 组件；三条 observability 支柱（component / experience / decision），**「every edit becomes a falsifiable contract」**；实测 **10 轮把 Terminal-Bench 2 pass@1 从 69.7% → 77.0%，超过人工设计的 Codex-CLI(71.9%)**，并做跨基准（SWE-bench-verified，token 少 12%）与跨模型族（+5.1~+10.1pp）泛化 + 消融 | ❌ 机制更完整、**且已完成本项目缺失的评估** |
| 3 | 缺陷/评审意见 → 持久化规范固化（缺陷必闭环） | **arXiv 2607.13091（Microsoft，2026-07-13，已被 ICE 2026 录用）**：每条被采纳的评审意见编码为持久行为规则 + 版本化指令文件 + 提交前自检清单 + 规则集完整性自动校验；**35+ 微服务生产部署，规则 5 → 18 条、语言标准 15+、自检清单 15 项，被规则覆盖的错误类复发率 0%**；并显式讨论「The Missing Benchmark」 | ❌ 与「缺陷必闭环」同构，**已同行评审 + 有生产度量 + 有复发率** |
| 4 | 宪法层（元规则）+ 失败模式登记 | **arXiv 2608.08311《Ouroboros》(2026-08-08)**：常驻编号 constitution + **pattern register**（复发失败 → error class / count / root cause / structural fix 的持久行，「instance-level patches → class-level prevention」）；带 Terminal-Bench 2.1 / OSWorld-Verified / SWE-bench Pro / GAIA 评估 | ❌ 概念重合，且对方有基准成绩 |
| 5 | 规范漂移门（spec ↔ code 漂移阻断） | **arXiv 2606.27045《Spec Growth Engine》(2026-06-25)**：把 spec-code 漂移做成 **blocking merge condition** | ❌ 已发表（D-05 §二.3 已引用） |

**补充（与 D-07 相关）**：D-07 声称「无人做过程合规 / 规范体系自身健康度」，实测至少已有 **Critical Gate**（repository-aware diff integrity gate，确定性优先、低噪声、LLM 可选）在公开推进同一方向。D-07 的「生态真空」表述应按「细分空白」而非「绝对空白」理解。

## 四、仍可发表的窄口子（3 条）

1. **「哪些缺陷配得上门禁」的判定程序**——准入门槛四问（可机检？零新依赖？真发生过？误报可控？）+ **1/4 固化率**经验。
   已发表工作都在回答「如何生长」，**无人回答「剩下 3/4 为什么长不出来」**——而这恰是门禁体系的真实瓶颈，也是唯一能形成独立命题的角度。
2. **宪法 ↔ 门禁的**双向**自校验**（红线缺门禁 = error，僵尸门禁 = warning）。
   Ouroboros 有 constitution，但未见「宪法与门禁清单互为约束」的机检机制；这是本项目 `check-constitution.*` 的差异化点。
3. **零新依赖约束下的门禁装配方言**（宿主优先级降级：复用既有入口 → Node → Python → make → shell 兜底）。
   属工程采纳视角，适合与 1 合并作为经验论文的「可落地性」支线。

**最小可行实验设计（若要投稿）**：

| 项 | 设计 |
|---|---|
| 语料 | N ≥ 10 个真实项目（本仓库 + 源项目 + 公开仓库），覆盖 ≥ 3 种语言 |
| 处置 | 记录每个项目的缺陷类清单 → 按准入门槛四问标注「可机检 / 不可机检」→ 计算固化率与原因分布 |
| 主指标 | 固化率（可机检比例）、错误类复发率、门禁误报率、单条门禁维护成本 |
| 对照 | 同一仓库「四问筛选后建门禁」vs「全量建门禁」（验证准入门槛是否真的降低误报） |
| 负向 | 僵尸门禁率（登记后 0 命中的门禁占比） |

## 六、必须正视的反向证据

1. **2604.25850 消融结论**：增益定位在 **tools / middleware / long-term memory**，而非 **system prompt**——「factual harness structure transfers while prose-level strategy does not」。
2. **ETH SRI（arXiv 2602.11988）**：context file **不普遍提升**任务成功率、推理成本 +20%。
3. 二者共同指向同一风险：**「把规范写进 AGENTS.md」这一主线的边际收益可能被高估**。本仓库 [D-08](D-08-外部评估复核报告.md) §4.4 已指出 README 中「Anthropic 基准减少 40-60% 错误模式重写」与 ETH 结论存在张力；本报告从文献侧补强该判断。

> 论文中若不同正面回应这条反向证据，会被审稿人直接击中；产品侧则应把卖点从「写了规范」调整为「规范可机检 + 门禁可生长」。
