# D-01 代码规范闭环增强方案

> 方案类型: 项目增强（Project Blueprint v1.7.0 候选）
> 提出日期: 2026-08-14 | 状态: **待评审** | 作者: 曙光 (shuguang1994)

---

## 一、背景与现状评估

### 1.1 问题描述

用户反馈：项目初始化后**没有实际写入基础代码规范**，代码规范体系存在明显缺口，主要体现在：

1. **基础规范缺失** — 生成的 AGENTS.md「强制规范」以组件级规范为主（如 NestJS/Vue 特定约定）+ 通用原则 7 条，缺少横向基础规范（命名、目录结构、错误处理、日志、安全、性能）。
2. **B-01 是占位符** — `docs/B/B-01-开发规范.md` 仅生成一行标题 + "待填写"，与实际编码脱节。
3. **文档间无引用闭环** — AGENTS.md 未声明与 B-01（详细规范）、B-04（BUG 知识库）的引用关系。
4. **BUG → 规范反哺缺失** — Step 7 只有「修复典型 Bug → 写入 B-04」，缺少「Bug 根因是规范不完善 → 更新规范规则」的动作，模型容易重复犯错。
5. **无进度提醒机制** — 没有按项目进度主动提醒用户维护 AGENTS.md 和相关文档。

### 1.2 评估结论

**值得优化**。理由：

- 代码规范是 AI 编程规范体系的核心交付物，当前"只有壳没有肉"，直接影响产品价值。
- 三层递进（知识库 → 启发 → 联网）、增量友好、零固定表等架构原则已成熟，本方案是**复用现有机制**而非新增复杂度。
- 反哺闭环是防模型重复犯错的必要手段，符合"一次修复、永久生效"的工程化诉求。

### 1.3 AI 高频错误专项评估

**结论：应作为最高优先级专项**，与 1.1 的通用缺口合并实施。

现状：AI 最容易犯的错误在现有体系中**只有碎片化覆盖**——

| AI 高频错误 | 现状覆盖 |
|------------|---------|
| 凭旧记忆写第三方库 API（版本差异） | ✅ 通用段落 1 条（v1.4.1 新增） |
| 重复引入已有依赖覆盖的新包 | ✅ 通用段落 1 条 |
| 绕过 api/ 封装直调底层 HTTP | ✅ 通用段落 1 条 |
| N+1 查询 / 无索引 | ⚠️ 仅各 ORM 条目零散提及 |
| 只走 happy path / 吞错误 | ⚠️ 审查清单提及，无规范条目 |
| 硬编码密钥 / 输入未校验 | ⚠️ 审查清单提及，无规范条目 |
| 滥用 any / 未处理空值 / 忘记 await | ⚠️ 语言层零散提及 |
| 绕过分层 / 全局可变状态 / console.log 遗留 | ⚠️ 框架层零散提及 |
| 命名随意 / 不读现有代码直接改 | ❌ 完全缺失 |
| push --force / 提交敏感文件 | ✅ Git 规范已覆盖 |

**专项价值**：本工具的核心服务对象是"AI 编程"，防 AI 高频错误 = 直接提升产品核心价值。将高频错误按「错误类型 × 技术栈」系统化为独立知识库，Step 2 生成 AGENTS.md 时**优先注入**对应规则，使初始化的规范体系天然具备"防 AI 犯错"能力，并与 B-04 反哺闭环形成迭代（AI 再犯 → 更新清单 → 防再犯）。

## 二、方案目标

建立 **AGENTS.md（核心）→ B-01（详细）→ B-04（反哺）三层代码规范体系**，实现：

1. 项目初始化时**实际写入基础代码规范**（大模型自身知识 + 种子知识库 + 联网搜索三层生成）。
2. 规范核心写入 AGENTS.md，详细规范写入 B-01，Bug 反哺写入 B-04，三者互相引用。
3. 工程化中因规范不完善产生的 Bug，自动反哺更新对应规范，防止模型犯相同错误。
4. AGENTS.md 注入维护提醒规则，按项目进度提醒用户维护 AGENTS 和相关文档。
5. **（专项）AI 高频错误防犯清单**：按「错误类型 × 技术栈」系统化 AI 最容易犯的错误，初始化时优先注入 AGENTS.md 核心规则，工程化中通过 B-04 反哺持续迭代。

## 三、总体设计

### 3.1 三层代码规范体系

```
┌─────────────────────────────────────────────────────────────┐
│ L1  AGENTS.md · 强制规范（核心，≤20 条，模型每次必读）          │
│     命名 / 错误处理 / 日志 / 安全 / 性能 / 组件级 ✅❌ 规则       │
│              │ 引用                                    ↑ 反哺  │
│              ▼                                          │      │
│ L2  docs/B/B-01-开发规范.md（详细，按需查询）                │      │
│     命名对照表 / 目录结构 / 错误码约定 / 日志规范 / 安全检查清单  │      │
│              │ 引用                                    ↑ 反哺  │
│              ▼                                          │      │
│ L3  docs/B/B-04-BUG知识库.md（实际 Bug 沉淀）                │      │
│     每个 Bug 含「规范反哺」字段：根因=规范缺失？→ 更新 L1/L2 哪条 │      │
└─────────────────────────────────────────────────────────────┘
```

**分工原则**（遵守 AGENTS.md 架构原则，控制规模）：

| 层级 | 内容 | 规模控制 |
|------|------|---------|
| L1 AGENTS.md | 模型每次编码前必读的**核心规则**（基础 5 类 × 各 ≤4 条 + 组件级） | 强制规范章节 ≤ 20 条，超限移入 B-01 |
| L2 B-01 | 详细规范：命名对照表、目录结构、错误码约定、日志格式、安全检查清单 | 不限，作为查询源 |
| L3 B-04 | 实际 Bug 记录 + 根因 + 修复 + **规范反哺** | 持续追加，季度归档 |

### 3.2 基础规范生成机制（Step 2 增强）

按探测到的语言/框架/ORM，从以下三层递进获取基础规范（复用 1.2/2.2 现有模式）：

```
第 1 层 — 种子知识库 references/code-conventions.md 精确匹配
  按「维度 × 语言」定位（如 命名规范 × TypeScript）
  命中 → 提取 ✅/❌ 规则（快速通道）
    ↓
第 2 层 — 大模型自身知识展开
  按种子条目的框架，结合探测到的技术栈展开具体规则
  （例：Vue 3 项目 → 组合式 API / 命名用 useXxx / 事件 kebab-case）
    ↓
第 3 层 — 联网搜索
  对不确定的规范点 → WebSearch "{语言}/{框架} code conventions best practices {currentYear}"
  搜索结果同时用于判断是否补充种子知识库
    ↓
输出: { 规范类别 → 核心规则（写入 AGENTS.md） + 详细规则（写入 B-01） }
```

**规则数量控制**：
- AGENTS.md 强制规范：基础 5 类（命名/错误/日志/安全/性能）× 每类 ≤4 条核心规则 + 组件级规则（现有）→ 总计 ≤ 20 条
- 其余详细规则全部落入 B-01

### 3.3 B-01 / B-04 实写（Step 3 增强）

**B-01-开发规范.md**（从占位符改为实写）：

```markdown
# 开发规范

> 详细编码规范。AGENTS.md 为权威源，本文件为详细展开。
> 技术栈: {Step 1 探测结果} | 更新: {date}

## 一、命名规范        （文件/变量/函数/类/组件/数据库，含对照表）
## 二、目录结构规范     （按项目结构生成）
## 三、错误处理规范     （错误码约定/异常类型/错误边界/前端四态）
## 四、日志规范         （结构化日志/级别/敏感信息脱敏）
## 五、安全规范         （输入校验/鉴权/密钥管理/注入防护）
## 六、性能规范         （N+1/索引/懒加载/缓存/构建优化）
## 七、技术栈特定规范    （从 knowledge-base 组件 Conventions 展开）
## 八、规范维护
     - 新增规范 → 先评估是否进 AGENTS.md 核心（≤20 条），否则放本文件
     - Bug 根因是规范缺失 → 补规则到对应章节 + 在 AGENTS.md 加一条防复发
```

**B-04-BUG知识库.md**（模板加入「规范反哺」字段）：

```markdown
## Bug #{编号}: {简述}
- 现象:      {错误表现}
- 根因:      {根因分析}
- 修复:      {修复方案}
- 是否规范缺失: 是/否
- 规范反哺:    {若是 → 补充 B-01 第X章规则 + AGENTS.md 强制规范新增 ✅/❌ 一条}
- 防止复发:    {预防措施}
```

### 3.4 AGENTS.md 注入三层引用（Step 2/7 增强）

强制规范章节末尾固定注入（模板化）：

```markdown
### 代码规范体系
✅ 强制规范为**核心规则**，详细规范见 docs/B/B-01-开发规范.md，Bug 反哺见 docs/B/B-04-BUG知识库.md
✅ 违反强制规范 = 违反项目约定，编码前先核对本章节
```

### 3.5 BUG → 规范反哺闭环 + 进度提醒（Step 7 增强）

**上下文管理表格新增两行**：

| 操作 | 更新内容 |
|------|---------|
| 修复 Bug 且根因是规范缺失 | 补充 B-01 对应章节规则 + AGENTS.md 强制规范新增一条 ✅/❌ 防复发 |
| 按项目进度检查（功能完成/重构/上线/季度） | 检查 AGENTS.md / B-01 / B-04 是否滞后于进度，滞后则提醒用户维护 |

**进度提醒机制**（新增段落）：

```markdown
## 项目进度与文档健康检查

- Agent 在以下里程碑主动检查文档滞后情况并提醒用户维护：
  | 里程碑 | 检查项 |
  |--------|--------|
  | 新功能完成 | 模块速查表 / 技术栈行 / 代码规范是否需补充 |
  | 重构完成 | 架构决策表 / 目录结构 / 耦合度分析 |
  | 上线前 | B-02 部署指南 / CI 描述 / 检查清单 |
  | 季度末 | 项目记忆清理 / B-04 归档 / 规范体系回顾 |
- 用户说"看下项目进度" → 输出：最近进展 + 文档滞后清单 + 建议维护项
```

### 3.6 AI 高频错误防犯专项（最高优先级）

**新增 `references/ai-common-mistakes.md`** — AI 高频错误知识库，按「错误类型 × 技术栈」组织，与基础规范互补：

```
## [错误类型]（依赖/API · 数据性能 · 错误处理 · 安全 · 类型语言 · 工程规范 · Git）
**AI 易错点**: 错误描述（模型为何会犯）
**后果**: 实际影响
**❌ 错误示范**: 典型错误代码片段
**✅ 正确做法**: 规范写法（写入 AGENTS.md 核心规则）
**关联知识库**: 对应 knowledge-base.md 组件条目（取 Conventions）
**搜索模板**: 未知技术栈时的联网搜索模板
```

**注入策略（Step 2 增强）**：

```
Step 2 拼接强制规范时：
  第 1 步 — 从 ai-common-mistakes.md 按探测技术栈提取对应「AI 易错点」
  第 2 步 — 基础规范 5 类（命名/错误/日志/安全/性能）核心规则**优先选取 AI 高频错误对应规则**
  第 3 步 — 未覆盖的错误点 → WebSearch "{language}/{framework} common mistakes anti-patterns {currentYear}"
  第 4 步 — 命中规则写入 AGENTS.md 强制规范（≤20 条上限内），详细内容落入 B-01
```

**B-01 新增章节**：

```markdown
## 八、AI 高频错误防犯清单
> 来源: references/ai-common-mistakes.md（按技术栈裁剪）+ B-04 反哺迭代
| 错误类型 | AI 易错点 | ✅ 正确做法 | ❌ 错误示范 |
```

**反哺闭环增强（Step 7）**：

```
修复 Bug 且根因是 AI 犯错时：
  ① 检查是否命中 ai-common-mistakes 清单
  ② 命中 → 强化对应规则（B-01 标注出现次数），确认 AGENTS.md 已有防犯规则
  ③ 未命中 → 新增清单条目 + B-01 补规则 + AGENTS.md 加一条 ✅/❌ 防复发
```

**代码审查清单增强**：新增「AI 高频错误检查项」（第三方库 API 已核对当前版本？无 N+1？错误路径已处理？无硬编码密钥？无 any？无 console.log？不绕过 api/ 封装？）。

| 风险 | 对策 |
|------|------|
| AGENTS.md 膨胀 | 核心规则硬性 ≤20 条，超限移入 B-01；沿用高内聚低耦合架构原则 |

## 七、验收标准

1. 新项目初始化后 AGENTS.md 强制规范含基础代码规范（≥ 命名/错误/日志/安全/性能 5 类）且 ≤ 20 条。
2. `docs/B/B-01-开发规范.md` 为实写内容（非占位符），含 8 章规范（含「AI 高频错误防犯清单」）+ 规范维护章节。
3. `docs/B/B-04-BUG知识库.md` 模板含「是否规范缺失 / 规范反哺」字段。
4. AGENTS.md 含「代码规范体系」三层引用 + 「项目进度与文档健康检查」章节。
5. 模拟一个规范缺失型 Bug，验证反哺链路：B-04 记录 → B-01 补规则 → AGENTS.md 加防复发规则。
6. **（专项）模拟 3 个 AI 高频错误场景**（如 TypeORM 0.2→0.3 旧 API、N+1 查询、绕过 api/ 直调 HTTP），验证初始化生成的 AGENTS.md 均命中对应防犯规则。
7. `references/ai-common-mistakes.md` 覆盖 ≥ 7 大类、每类 ≥ 3 条跨语言条目，且每条含 易错点/后果/❌示范/✅做法/搜索模板。

## 八、待确认决策点

> 以下为作者建议（2026-08-14），供评审确认。确认后按建议执行，如需调整请指出。

### 决策 1：基础规范生成时机

- **建议：初始化即生成（一次到位）**
- 理由：
  - 本方案解决的痛点就是"初始化后没有实际写入规范"，延迟到里程碑生成等于未解决核心诉求。
  - 规范是纯文本，生成成本极低；模型从第一天就遵循，避免前期开发违规后的返工。
  - 与 Step 6 测试制度不同（测试有代码成本，项目初期可不写），规范生成无此顾虑。
  - 现有"增量友好"设计保证已有项目接入只补缺失，不因初始化生成而破坏。

### 决策 2：种子知识库 code-conventions.md

- **建议：内置 6 大类种子**
- 理由：
  - 与 knowledge-base.md（70+ 组件）同一设计哲学：种子提供**确定性基线**，模型知识 + 联网负责展开补充。
  - 纯模型+联网的缺点：生成结果不稳定（跨模型/跨时间），且网络不可用时无下限。
  - 静态种子一次编写长期复用，成本可忽略；种子只给"分类框架 + 高频规则 + 搜索模板"，具体项目规则仍由 Step 2 三层递进拼接，保持零固定表哲学。

### 决策 3：AI 高频错误清单 ai-common-mistakes.md

- **建议：内置独立知识库（不与 code-conventions.md 合并）**
- 理由：
  - 这是最高优先级专项，必须有确定性基线；AI 高频错误是**已知问题**，可预先系统化，无需每次联网。
